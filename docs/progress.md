### Fresh-volume portability test (the actual point of this phase)
Tore down all containers *and volumes* (`docker compose --profile tools down -v`) to simulate a
genuinely fresh checkout, then rebuilt and brought the stack up from nothing. This caught two real
bugs that a quick manual spot-check would have missed:

- **Bug 1 — `docker compose build` silently skips profiled services.** `migrate`/`seed`/
  `dataquality` carry `profiles: ["tools"]` (by design, so they never auto-start). A bare
  `docker compose build` only rebuilds default-profile services — it silently left `migrate`
  running a stale image built before the data-quality and evaluation migrations existed. Running
  `migrate` against the fresh volume applied only the first of three migrations and stopped with
  no error, because Alembic correctly considered that stale image's single migration file "head."
  Fix: rebuild profiled services explicitly with `docker compose --profile tools build`. This is
  now the documented way to rebuild everything from a clean checkout — a plain `docker compose
  build` is not sufficient.
- **Bug 2 — `Dockerfile.migrate` was missing `app/evaluation/eval_models.py`.** `alembic/env.py`
  imports `eval_models` so autogenerate can see the evaluation tables; the Phase 4 migration
  landed without ever updating `Dockerfile.migrate`'s COPY list to match (previously masked by
  reusing an already-migrated dev volume, which never re-ran `env.py`'s imports against a truly
  fresh target in a freshly-built image). Fixed by adding `app/evaluation/{eval_models.py,
  __init__.py}` to the image.

Both were only found because this phase does what its name says — proves it from zero, not from a
machine that's accumulated months of incremental state. After both fixes: fresh volume → `migrate`
(all 3 migrations apply, 15 tables + `alembic_version` confirmed via `\dt`) → `seed` (2000
candidates / 1000 jobs confirmed) → `dataquality` (10/10 checks pass) → `api` + `mlflow` (both
report healthy) → real API calls succeed with the `.env`-configured key. Full test suite (53
tests) still passes throughout.

### Decisions
- `docker/postgres-init/01-create-mlflow-db.sql` still hardcodes the literal database name
  `mlflow` (init scripts run before any app code and can't read compose env var substitution) —
  documented in the file that it must be kept in sync with `.env`'s `MLFLOW_DB_NAME` if ever
  changed from the default. Not worth a templating mechanism for a single literal in a dev-only
  default.
- `docs/assumptions-register.md` A7/A9 updated: secrets now live in `.env` (git-ignored) instead of
  the compose file itself — meaningfully better for a published portfolio repo (no credentials in
  git history going forward) — but values are still local-dev placeholders, not rotated/managed
  secrets; the "before any shared/deployed environment" trigger is unchanged.

### Getting the pushed pipeline actually green (2026-10-29)

The first pushed run was not green — verified via the GitHub Actions API (polled run/job status
directly, not assumed), and each failure was root-caused from the API's annotations/step data
rather than guessed at:

1. `aquasecurity/trivy-action@0.28.0` — wrong tag format (real tags are `v`-prefixed); every
   `build-and-scan` matrix job failed at action-resolution time before any step ran.
2. `aquasecurity/trivy-action@v0.28.0` (tag fixed) still failed the same way — that specific
   release's pinned nested action, `aquasecurity/setup-trivy@v0.2.1`, no longer exists upstream
   (earliest available tag is `v0.2.6`). Bumped to `trivy-action@v0.36.0`, which pins its
   `setup-trivy` dependency by commit SHA instead of a floating tag.
3. With all `build-and-scan` jobs passing, `fresh-volume-smoke-test` failed at "wait for db
   healthy" — `docker inspect jme-db-1` found no such container. Root cause: Compose derives its
   project name (and therefore container names) from the current directory when none is pinned;
   locally that's `JME` (-> `jme-db-1`), but a GitHub Actions checkout uses the repo name
   `match-engine-platform` (-> `match-engine-platform-db-1`). Fixed by adding a top-level `name:
   jme` to `docker-compose.yml`, making container names identical in both environments.

Four pushes total to get from "pipeline authored" to "pipeline verified green end-to-end" — each
fix confirmed by actually polling the GitHub Actions API for the next run's result, not assumed
from reading the diff. Final run (`40942700618`): all jobs green, including the full fresh-volume
sequence (migrate → seed → dataquality → api/mlflow → authenticated API call) on a genuinely clean

## Phase 17 — Multi-dimensional embedding matching, Use Case F groundwork (2026-10-30)

Resolves assumption A5's promise, deferred since Phase 4: *"Phase 4 evaluation report will state
measured delta between rule-based and semantic approaches before any decision to adopt."* Also the
architecture needed to eventually score one candidate against 100,000+ jobs — a vector database's
ANN index, not brute-force, is what makes that affordable at all.

**Built and verified, not assumed**:
- Swapped `docker-compose.yml`'s `db` image to `pgvector/pgvector:0.8.7-pg16` — confirmed via
  Docker Hub's API as a genuine drop-in Postgres 16 build, not a fork. Recreated the running
  container against the existing volume; every prior table's row counts survived unchanged. A
  collation-version warning (base-image glibc difference) was fixed with Postgres's own documented
  `ALTER DATABASE ... REFRESH COLLATION VERSION` — a one-time local fix only, irrelevant to CI's
  always-fresh volumes.
- A real technical decision, not a workaround: split a **production** `entity_embeddings` table
  (pgvector HNSW-indexed, one active model per dimension — what stage-1 ANN retrieval actually
  queries) from an **evaluation** `embedding_eval_results` table (plain JSONB, freely swappable
  models) — resolves pgvector's fixed-vector-width constraint cleanly rather than fighting it.
- Three embedding dimensions: Skills (free — reuses Phase 16's cached per-skill embeddings, zero
  new LLM calls), Experience and Overall (synthesized text from real structured fields, one
  embedding call each). Education dimension explicitly not built — no real data source, same
  discipline as the qualification-compatibility omission already documented in
  `docs/matching-engine.md`.
- Computed real embeddings for all 1,000 jobs and 80 candidates with `all-minilm` (384-dim).
  Invalidation verified, not assumed: a second run against the same data correctly skipped all 240
  already-computed rows via `source_hash`, recomputing zero.
- Two-stage retrieval wired into a new endpoint, `GET /candidates/{id}/job-matches/semantic` —
  confirmed to make **zero live Ollama calls**: embeddings are precomputed offline, retrieval is
  pure pgvector ANN plus in-Python blending with the existing rule-based location/salary/
  occupation components, returning ranked results over the full 1,000-job population with no
  visible latency.
- Near-miss similarity threshold calibrated from real measurement (not guessed): embedding the
  12 hand-labeled skill pairs with `all-minilm` showed a clean gap between "similar" pairs
  (0.315–0.649 cosine) and "dissimilar" pairs (0.145–0.252) — 0.28 sits in that gap, scoring 100%
  accuracy on the set.
- **The actual measured comparison** (30 candidates with both ground truth and embeddings, k=10):
  rule-based P/R/NDCG/MRR = 0.52/0.862/0.849/0.881; blended = 0.523/0.852/0.875/0.933 (a real,
  modest NDCG/MRR improvement); embeddings-only = 0.497/0.791/0.776/0.815 (underperforms
  rule-based-only — explainable, since Phase 4's ground truth is itself an exact-occupation-match
  label the rule-based score's own occupation component already answers almost perfectly). Rule-
  based stays the default; the semantic endpoint is additive, not a replacement — the outcome this
  measurement existed to determine, not assume.
- Wired into CI (fresh-volume-smoke-test: computes a small embeddings sample, smoke-tests the new
  semantic endpoint with a real pgvector ANN query). 20 new tests, 116 total passing.

**Explicitly not done in this phase**: Education dimension, courses dimension (separate topic per

justify it), a real 100,000-job stress test (architecture designed for it, only verified at 1,000),
Qdrant migration (not triggered — no measured pgvector limitation exists).

- **Extraction (C)**: threshold sweep (0.45/0.50/0.55/0.60/0.65) confirmed the original 0.55 was

- **Embeddings (F)**: compared `all-minilm` (v1 production default) against `nomic-embed-text` on
  the 12-pair near-miss set — **the smaller model won**: `all-minilm` cleanly separated every pair

  actually *overlapped* (best achievable 92%, no single threshold separates all 12). `all-minilm`

**4. Soak test** (previously only a short point-in-time load test): `scripts/load_test.py
--soak-minutes` runs continuously and reports one summary per time window instead of one aggregate
number — the only way to see a trend, not a snapshot. A real 3-minute run (concurrency=10, 30s
windows) against the `--workers 4` fix from Phase 13 showed stable p50 (~0.17–0.18s) and throughput

**5. Basic rate limiting** (previously none): `slowapi`/`limits`, in-memory, keyed by API key

counter — a real test (150 rapid sequential requests, one key) let 122 through before 429s, not a
clean 100, because the "global" limit is actually 4 uncoordinated per-process limits. **This is the
first concrete, measured case in this project where Redis (a shared counter store) would provide
real value**, turning the earlier "do we need Redis?" question from hypothetical into a documented,
specific trigger — not fixed in v1, since `api`'s limit still meaningfully bounds abuse even if
imprecise. Also found and fixed a related interaction bug before it shipped: `analytics`'s
ingestion routes would have been rate-limited into silently dropping events under real load (a
soak-test-measured ~2,280 instrumentation calls/minute blows past any reasonable numeric limit,
and that endpoint doesn't raise on failure by its own best-effort design) — exempted instead,
verified under a real 30-request burst that exactly 300 events (30×10) landed, zero dropped.

**Explicitly not done in this phase**: real secrets manager, TLS, OAuth2/JWT/roles, real Azure
deployment — all deliberate scope boundaries (would mean real cloud spend or inventing
infrastructure for a user-model problem this project doesn't have), not oversights. An hours-long

## Phase 19 — Knowledge graph: candidates/skills/occupations/jobs/courses (2026-10-30)

In response to "can we create a knowledge graph service... what do you think?" Deliberately picked
a heavier tool (Neo4j + GDS) than the project's usual "simplest thing first" default, because the
problem — multi-hop relationships, community detection, centrality — is genuinely graph-shaped and
because demonstrating a real graph database has direct portfolio value, which the user explicitly
asked for.

**A real course-correction during design, prompted by the user pushing back**: the design doc
initially avoided Neo4j's GDS plugin over an inconclusive licensing search. Asked "is it not a
powerful way to explore structures — why not use it?" — dug further and verified directly instead
of leaving it ambiguous: Neo4j's own docs confirm Community Edition includes every GDS algorithm
(Enterprise-only features are backup/restore and Arrow import/export, neither relevant), capped
only at 4 CPU cores. Installed the plugin into a disposable test container and watched the startup
log itself print `GDS license state: unlicensed` — the documented free mode — then ran a real
`gds.louvain.stream()` call successfully. Design corrected before any production code was written.

**Built and verified, not assumed**:
- `neo4j:5.26.32-community` (official image) + `NEO4J_PLUGINS=["graph-data-science"]`, always-on
  (Neo4j Browser needs to be reachable, not just during a batch job) — confirmed reachable
  (`HTTP 200` at `localhost:7474`).
- `app/graph/sync_graph.py` — idempotent batch ETL (`MERGE`, not `CREATE`) from Postgres into
  Neo4j, mirroring every existing relational entity/junction table one-to-one, plus one aggregated
  `ENGAGED_WITH` edge derived from Phase 14's `behavioral_events` log (a deliberate cross-phase
  tie-in). Ran against the full seeded dataset: 64 `Skill`, 150 `Occupation`, 100 `Course`, 2,000
  `Candidate`, 1,000 `Job` nodes; 11,814 `HAS_SKILL`, 6,034 `REQUIRES_SKILL`, 908
  `SKILL_OF_OCCUPATION`, 195 `TEACHES_SKILL`, 1,899 `TARGETS_OCCUPATION`, 1,000
  `POSTED_FOR_OCCUPATION`, 34,788 `ENGAGED_WITH` edges. Idempotence verified by re-running:
  identical counts, confirmed independently via `cypher-shell`, not just the job's own output.
- `app/graph/cluster_skills.py` — skill co-occurrence derivation + Louvain community detection
  running entirely server-side via GDS/Cypher (`gds.graph.project` + `gds.louvain.write`), no
  Python graph-algorithm library needed at all.
- **A real, root-caused finding, reported honestly rather than hidden**: the clustering result is
  weak (modularity 0.045, mean category purity 0.16 — barely above random chance). Investigated,
  not just reported: the co-occurrence graph turned out to be *complete* (2,016 edges = exactly
  64-choose-2, every possible skill pair), traced to `generate_synthetic_data.py`'s occupation-skill
  sampling being uniform-random across all 64 skills with no category weighting. Tested whether
  pruning weak edges would help (it didn't — even stricter thresholds collapsed almost everything
  into one giant community) before concluding this is a genuine property of the existing Phase 2
  dataset, not a bug in this phase's code. Explicitly **not** fixed by changing the Phase 2
  generator — that would regenerate the dataset and invalidate every downstream measured baseline
  (Phase 4's P@10/NDCG, Phase 16/17's golden-dataset numbers) that depends on the current
  `SEED=42` distribution — a user-confirmed decision to report honestly rather than retrofit the
  data to flatter this phase's result.
- Wired into CI (`build-and-scan` matrix, `fresh-volume-smoke-test`: starts neo4j, runs the real
  sync job, confirms nodes exist, runs the real clustering job). 7 new tests (pure-logic: batching,
  purity calculation), 134 total passing.

**Explicitly not done in this phase**: no live query API (Neo4j Browser/Cypher only), no
candidate/job-level clustering (skills only), no graph-based signal feeding into Phase 17's
matching blend yet (the documented v3 connection point, not built), and the clustering signal
itself remains weak pending a possible future, carefully-scoped generator enhancement (not
attempted here).

### Phase 19 — status: v1 COMPLETE (graph + sync + native GDS clustering all verified; clustering signal honestly weak, root-caused, not hidden)

## Phase 20 — Realistic, scalable synthetic data generation (2026-10-31)

In response to wanting data that produces genuinely interesting knowledge-graph insights, plus a
LinkedIn-scale architecture target (~1M users, ~50K jobs). Fixes Phase 19's root-caused finding and
proves the architecture at real scale in the same pass — deliberately, since there's no point
stress-testing a generator that still produces data with no structure in it.

**Built and verified, not assumed**:
- **Domain-anchored skill sampling**: occupation skill profiles now draw ~70-80% from one of four
  coarser "domains" (grouping the existing fine-grained categories) plus ~20-30% random noise,
  replacing uniform-random sampling across all 64 skills. Cascades automatically to candidates/jobs
  since they already derive their pools from occupation profiles — no other code changed.
- **Bulk-insert, chunked generation**: candidates/jobs and their skill-junction tables now use
  batched `executemany`-style Core inserts (10,000 rows/batch) with explicit sequential IDs,
  replacing one-row-at-a-time ORM inserts. Default scale (2,000/1,000) unchanged — every existing
  baseline keeps its exact prior measurement context; a new `--scale large` invocation targets the
  real deployment goal.
- **The actual 1M/50K stress test, run for real**: `--scale large` generated 1,000,000 candidates,
  50,000 jobs, 3,000 occupations, 2,000 courses, and ~6.4M skill-junction rows (~7.4M rows total)
  in **11m40s**. Full graph sync into Neo4j (via Phase 19's `sync_graph.py`, unchanged) completed
  in **15m50s** for ~1.06M nodes and ~6.4M edges.
- **Domain fix validated, before/after, not assumed to help**: re-ran Phase 19's clustering —
  mean category purity 0.1585 → **0.3222**, and all 4 discovered communities now map **exactly
  1:1** onto the 4 designed domains with zero cross-contamination (previously no correspondence at
  all). The co-occurrence graph is still topologically complete, but its edge *weights* are now
  sharply differentiated (min 42/max 335 vs. the old min 3/max 83) — sufficient for weighted
  Louvain without needing graph sparsity, a more precise finding than "fixed it."
- **A real N+1 bug found by the stress test itself, not code review**: at 50,000 jobs, rule-based
  ranking took 3.5s/candidate (consistent with Phase 9's measured per-job rate × 50x more jobs) —
  expected and architecturally understood. But the *embeddings* path, supposedly immune to job-count
  scaling via ANN retrieval, took an unexpected 1.637s with only 300 jobs embedded. Traced to
  `app/embeddings/retrieval.py` calling `load_job_profile` + three `_get_vector` queries **per job**
  in the stage-2 loop — the exact N+1 pattern Phase 9 already fixed once, reintroduced here. Fixed
  with new batch-loading functions (`load_job_profiles_by_ids`, `_get_vectors_batch`); re-measured
  at **~0.11–0.21s**, a ~10-15x improvement, confirmed live via the real `/job-matches/semantic`
  endpoint (10.7s rule-based vs. 1.2s semantic over HTTP at full 50,000-job scale) — the concrete,
  measured case for Phase 17's two-stage architecture, not a theoretical argument for it.
- **Every downstream baseline re-verified, not left stale**: Phase 4/9 matching quality stayed
  essentially stable (expected — occupation-alignment ground truth didn't change). Phase 16
  extraction held at F1 0.6766 (consistent with its earlier tuned range). **Phase 17's
  rule-based-vs-embeddings comparison reversed**: embeddings-only now beats rule-based-only
  (NDCG 0.798 vs. 0.645) where it previously lost (0.776 vs. 0.849) — a direct, measured
  consequence of skills finally carrying real domain signal, not a coincidence.
- A transient `httpx.ReadError` hit two separate long-running Ollama calls mid-session — traced to
  an 8-hour gap in `ollama`'s own logs (02:32 → 10:42), meaning the host machine slept mid-request
  and broke the open connections. Not a code or Ollama stability bug; both jobs succeeded cleanly
  on retry, and the hash-based incremental design meant no already-committed progress was lost.
- 6 new tests (domain-coverage completeness, anchored-sampling ratio, the new batch-loading
  function), 140 total passing.

**Explicitly not done in this phase**: the 1M/50K dataset was generated, measured, and then the
standing dataset was reverted to the (now domain-fixed) small scale for day-to-day consistency with
every other doc/test/CI check — the large-scale run was a stress test, not a permanent change to
what's running. Candidate/job-level graph clustering, full-population embeddings/extraction at
1M/50K scale (sampled only, by design), and promoting blended to the default ranking path all
remain open, documented next steps.

### Phase 20 — status: v1 COMPLETE (domain fix verified, 1M/50K scale proven, a real N+1 bug found and fixed, every downstream baseline refreshed)

## Phase 21 — Redis: rate limiting, result caching, async streaming (2026-10-31)

Second half of the user's own two-part request ("then i need redis as well ... redis will be
required to handle asynchronous calls etc and storing active user session results for atleast 1
hour"). Design doc written and reviewed first (`docs/redis-infrastructure.md`), same discipline as
every prior phase — three independently-scoped use cases, not "add Redis" as a vague capability.

**Built and verified against real running containers, not assumed from the design**:
- One shared `redis:7.4.12-alpine` service added to `docker-compose.yml` (official image,
  confirmed via Docker Hub's API), a dependency of `api` and `analytics` only — `extraction` was
  left out, consistent with the design doc's service boundary (it runs a single worker, so Phase
  18's multi-worker rate-limit bug never applied to it).
- **Use case 1 — rate limiting, re-measured a real fix, not just a code change**: `app/api/
  rate_limit.py` and `app/analytics/rate_limit.py` now pass `storage_uri=REDIS_URL` to `slowapi`'s
  `Limiter` when it's configured, falling back to in-memory storage otherwise (so a bare `pytest`
  run with no Redis container behaves exactly as before). Re-ran Phase 18's exact test — 150 rapid
  concurrent requests, one API key, against `/candidates/1/job-matches` — against the fix: **100
  succeeded, 50 got 429s**, a clean split replacing the old ~122-through inflation across `api`'s 4
  worker processes. Checked directly (not assumed) that `api` and `analytics` sharing one Redis
  instance for this doesn't cross-contaminate their counters: `slowapi` scopes its Redis key by
  `(key_func_result, endpoint_identity)`, and the two services' endpoint functions are never named
  the same — verified by instantiating `limits.storage.RedisStorage` directly and inspecting the
  actual keys it writes.
- **Use case 2 — 1-hour cache-aside result caching**: `app/api/cache.py`, wired into both
  `/candidates/{id}/job-matches` and the `/semantic` variant, with an `X-Cache: HIT`/`MISS` response
  header. Verified live: first call to a candidate's job-matches returned `MISS`, the identical
  second call returned `HIT`, and `redis-cli TTL` on the stored key showed ~3590 seconds remaining
  — a real 1-hour TTL, not just a config value nobody checked. Fail-open by design: a Redis read/
  write error is caught and logged, never raised, same doctrine as the Phase 14 analytics hook.
- **Use case 3 — Redis Streams replacing the analytics instrumentation hook's synchronous HTTP
  call**: `app/api/stream_client.py` (producer, `XADD`) and `app/analytics/stream_consumer.py`
  (consumer, a background thread started from `app/analytics/main.py`'s lifespan handler,
  `XREADGROUP`/`XACK`, ack-after-write only). `app/api/analytics_client.py` tries the stream first
  and falls back to the original HTTP POST only when `REDIS_URL` isn't configured — both the
  decoupled path and the existing `/events`/`/events/batch` HTTP endpoints coexist. Verified live:
  `XINFO GROUPS analytics:recommendation_events` showed `pending: 0` with `entries-read` matching
  `XLEN` exactly (the consumer keeps up with zero backlog), and the actual rows landed in
  `analytics.behavioral_events` with correct `actor_id`/`entity_id`/`metadata` content — the stream
  path is behaviorally equivalent to the old HTTP path, just durable across an analytics outage now
  instead of silently dropping events.
- `.github/workflows/ci.yml`'s `fresh-volume-smoke-test` job extended with real checks for all
  three use cases (the Streams-delivery check, an `X-Cache` MISS-then-HIT check, and a 150-request
  rate-limit check) rather than only re-running at the design-doc level.
- 6 new tests (`tests/api/test_cache.py`, `tests/api/test_stream_client.py`,
  `tests/analytics/test_stream_consumer.py`), 146 total passing. All pass with `REDIS_URL` unset
  (the CI `lint-and-test` job's environment) — the fail-open design is exercised for real by the
  test suite, not just argued in a docstring.

**Explicitly not done in this phase**: active cache invalidation on profile/job changes (TTL-only
in v1, a documented staleness bound), consumer-group failure handling for a crashed consumer
(`XPENDING`/claim logic — basic ack-after-write only), and splitting cache/broker onto separate
Redis instances — all deferred to a v2, only if actually needed (see
`docs/redis-infrastructure.md` "Known limitations").

### Phase 21 — status: v1 COMPLETE (all three use cases built and independently verified against real containers)
