## Phase 2 follow-up — Decouple ingestion / migrate / api (2026-10-28)

### Done
- Restructured `app/` into `app/ingestion/` (source schema + synthetic data generator, simulating
  an upstream data-engineering pipeline), `app/api/` (FastAPI service), and shared `app/db.py`.
- Split `requirements.txt` into `requirements-base.txt`, `requirements-api.txt`,
  `requirements-ingestion.txt`, `requirements-migrate.txt`, and a dev-only union
  `requirements-dev.txt`.
- Three separate Dockerfiles: `Dockerfile.api` (production, lean), `Dockerfile.migrate` (one-off
  Alembic job), `Dockerfile.seed` (dev/local-only data generator, never shipped to prod).
- `docker-compose.yml`: `migrate` and `seed` added as one-off services under `profiles: ["tools"]`
  so they never start on a plain `docker compose up`.
- Generator no longer owns DDL — removed `drop_all`/`create_all`, replaced with
  `TRUNCATE ... RESTART IDENTITY CASCADE`. Schema is owned exclusively by Alembic migrations.
- **Verified end-to-end**: fresh volume → `docker compose run --rm migrate` (creates 11 tables) →
  `docker compose run --rm seed` (2000 candidates, 1000 jobs confirmed via SQL count) →
  `docker compose up -d api` → `/health` and `/readiness` both return 200. Local pytest suite
  (2 tests) passes against the new import paths.
- Noted and documented trade-off: API image grew slightly (245MB → 289MB) because it now bundles
  SQLAlchemy/psycopg2 ahead of Phase 3's need to query the database — a deliberate choice, not an
  oversight. Full rationale: `docs/adr/0001-decouple-ingestion-migrate-api.md`.

## Phase 2 follow-up — Data quality checks (2026-10-29)

### Done

  calls, not ground truth.
- Alembic migration generated and applied; `docker-compose.yml` `dataquality` one-off service

- **Verified**: ran twice (once locally via venv, once via the containerized service) against the
  seeded dataset — all 10 checks passed both times, recorded as run #1 and run #2, measured rates
  match known generator targets.
- **Bug caught and fixed during build**: `CheckStatus.pass_` was being stored as the literal
  string `"pass_"` (Python enum member name) instead of `"pass"` (its value) — would have shown
  wrong on a future dashboard. Fixed via `values_callable`; caught by querying actual stored rows,
  not just trusting the printed output. Full writeup: `docs/data-quality.md`.
- 6 new unit tests for the pass/warn/fail threshold logic (8 total tests now passing).

## Test layout — mirror source packages, not Docker images (2026-10-29)

Restructured `tests/` into `tests/api/` and `tests/ingestion/`, mirroring `app/api/` and
`app/ingestion/` — not the Docker image boundaries (`api`/`migrate`/`seed`/`dataquality`), since
those are a many-to-many relationship with source files (e.g. `app/db.py` ships in every image;
`quality_models.py` ships in both `migrate` and `dataquality`) and would force test duplication.
Verified: all 8 tests still pass after the move (`git mv`, history preserved).

Noted for later: current tests are all pure unit tests (no DB/Docker required). The manual
build-and-curl verification done throughout this project (e.g. confirming containers are
healthy, row counts match) is effectively integration/smoke testing and should eventually become
scripted tests under `tests/integration/` — not built yet, since no such tests exist to move, but
the distinction matters for Phase 8 CI design (fast unit tests run always; slower integration
tests run less often).
