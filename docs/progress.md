## Test layout — mirror source packages, not Docker images (2026-10-29)

Restructured `tests/` into `tests/api/` and `tests/ingestion/`, mirroring `app/api/` and
`app/ingestion/` — not the Docker image boundaries (`api`/`migrate`/`seed`/`dataquality`), since

Verified: all 8 tests still pass after the move (`git mv`, history preserved).

Noted for later: current tests are all pure unit tests (no DB/Docker required). The manual
build-and-curl verification done throughout this project (e.g. confirming containers are
healthy, row counts match) is effectively integration/smoke testing and should eventually become
scripted tests under `tests/integration/` — not built yet, since no such tests exist to move, but
the distinction matters for Phase 8 CI design (fast unit tests run always; slower integration
tests run less often).

## Phase 3 follow-up — Course recommendations, Use Case E (2026-10-29)

### Done
- `app/matching/course_recommendations.py`: occupation-target skill gap (reuses `OccupationSkill`
  from Phase 2 as the skill-frequency/importance table — no new schema needed) +
  `recommend_courses()` ranking by importance-weighted coverage + DB-aware
  `recommend_courses_for_candidate()` entry point.
- Design note: this is a *different* kind of gap from `skill_gap.py` (Use Case D) — gap against a
  candidate's target occupation profile, not against one specific job posting.
- Added 3 loader functions to `profiles.py`: `load_occupation_skill_profile`,
  `load_course_skill_coverage`, `load_course_titles`.
- 6 new unit tests (pure, no DB) — 33 total tests now passing.
- **Verified against real data**: candidate without 3 occupation-relevant skills got 5 ranked
  course recommendations; top result (Java Bootcamp) correctly outranked a course where the same
  skill was only a minor tangential match (React Fundamentals) — a real demonstration of the
  scoring discounting weak matches on intentionally noisy synthetic course data.
- `docs/matching-engine.md` updated with full design + verified example output.
- Candidates without a `primary_occupation_id` (~5% by design) explicitly cannot use this use
  case yet — raises rather than silently returning an empty/misleading result.

### Explicitly deferred
- Multi-course "set cover" optimization (minimal combination of courses closing the whole gap).
- Use Case C (free-text skill extraction).

### Decision — Use Case C deferred, will skip the rule-based step (2026-10-29)
User's call: rule-based/dictionary skill extraction from free text won't adequately handle real
phrasing variety for this use case, unlike the rest of the matching engine where a deterministic
baseline came first. Use Case C is deferred entirely; when resumed, goes straight to NLP/
embedding-based extraction, built and evaluated properly rather than assumed to work. This is a
documented exception to the general "start simple, add ML only if proven necessary" pattern —
see assumption A5b in `docs/assumptions-register.md`.

## Phase 4 — Evaluation (2026-10-29)

### Done
- `app/evaluation/metrics.py`: Precision@K, Recall@K, NDCG@K, MRR — pure functions, 14 unit tests.
- `app/evaluation/ground_truth.py`: occupation-alignment ground truth, deliberately independent
  of the scoring formula being evaluated (avoids circular evaluation — see
  `docs/evaluation-strategy.md` for the reasoning). 1,899/2,000 candidates have usable ground
  truth (101 excluded, matching the known ~5% missing-occupation rate almost exactly).
- `app/evaluation/eval_models.py` + migration: `evaluation_runs`/`evaluation_candidate_results`,
  same two-level historization pattern as data quality.
- `app/evaluation/run_evaluation.py`: orchestrator, `config_label` captures exact scoring weights
  used so future weight changes are comparable against this baseline.
- **Measured (not guessed) the sample size decision**: timed actual ranking latency (~1.95s/
  candidate, consistent with the known N+1 query limitation) before picking a sample of 50 rather
  than the full 1,899-candidate population (would take over an hour).
- **Baseline established, run #1**: Precision@10=0.47, Recall@10=0.7458, NDCG@10=0.7283,
  MRR=0.8029, against current weights (skill=0.55, location=0.15, salary=0.15, occupation=0.15).
  Verified persisted correctly in both tables.
- `docs/evaluation-strategy.md` written: full methodology, honest reading of the baseline
  numbers, known limitations.

### Explicitly not done in this phase
- No comparison of alternative scoring weights yet — run #1 is a baseline only.
- Full-population evaluation (deferred to Phase 9, pending the N+1 query fix).
- No DB-fixture-based tests for `ground_truth.py`/`run_evaluation.py` — verified manually against
  real data instead, consistent with how `rank.py`/`data_quality.py` were verified.

## Phase 4 follow-up — MLflow experiment tracking (2026-10-29)

### Done
- MLflow added as an always-on service (`docker/Dockerfile.mlflow`, port 5000), not a one-off
  job — its UI/API needs to be reachable at any time to browse past runs, unlike migrate/seed/
  dataquality. Backend store: a dedicated `mlflow` Postgres database on the same instance
  (`docker/postgres-init/01-create-mlflow-db.sql` for fresh environments; created manually on
  the existing dev volume since Postgres only runs init scripts on first volume creation).
- Deliberate split, not duplication: MLflow tracks run-level params/aggregate metrics (browsable
  experiment history); Postgres `evaluation_candidate_results` keeps per-candidate detail
  (different consumer — future dashboard drill-down).
- `run_evaluation.py` logs to MLflow after persisting to Postgres; best-effort (a failed MLflow
  log doesn't fail the run).
- **Bug caught and fixed during verification**: first live run crashed with `UnicodeEncodeError`
  (MLflow's confirmation emoji print, incompatible with this Windows console's cp1252 encoding),
  leaving a run stuck in `RUNNING` status even though metrics had already logged successfully —
  confirmed via MLflow's REST API before concluding the data was intact. Fixed via MLflow's own
  `MLFLOW_SUPPRESS_PRINTING_URL_TO_STDOUT` flag; stuck run deleted once the fix was verified on a
  clean re-run (`eval-run-3`, status `FINISHED`).
- `app/requirements-evaluation.txt` uses `mlflow-skinny` (client only, no UI/server deps) —
  same "don't ship unused dependencies" discipline applied to the API/dataquality images.
- Full test suite (47 tests) still passes; 3 legitimate runs preserved in Postgres, 1 clean run
  in MLflow.

  exposed, per the Phase 3 note). Three endpoints added, each a thin translation layer only — no
