# Product Requirements Document — Job Matching Engine (JME) Portfolio Platform

Status: v1.0 — all 13 phases of the implementation plan complete (see `docs/progress.md`); this
PRD's own Definition of Done (Section 9) and Open Questions (Section 10) updated to reflect what
was actually built vs. deferred, not left as the original draft's unchecked boxes
Owner: Usman (independent portfolio project)
Last updated: 2026-10-29

## 1. Problem Statement

Organizations that place job seekers into jobs (workforce development agencies, HR platforms,
staffing providers) need to match candidates to opportunities at scale, explain *why* a match was
made, identify skill gaps, and recommend learning paths to close those gaps — while keeping
decisions auditable and avoiding opaque "black box" scores.

This project builds a standalone, independently designed Job Matching Engine and Recommendation
Platform that demonstrates how to architect, build, secure, deploy, and operate such a system end
to end, using only synthetic data and open tooling.

## 2. Confidentiality Boundary (hard constraint)

This is an independent implementation, not a reproduction of any employer's system.

- No confidential datasets, source code, proprietary schemas, SQL, credentials, or internal
  architecture documents from any prior employer engagement are used, referenced, or consulted
  during design or implementation.
- All data is synthetic, generated by this project's own scripts with a fixed seed.
- All schemas, scoring logic, and architecture are designed from scratch for this project.
- This system must never be represented as an official or derivative version of any employer's
  production system.

## 3. Objective

Build a reusable, modular platform that ingests synthetic job-seeker and job-posting data,
computes matches and recommendations, exposes them via API, and can be deployed, monitored,
secured, and operated the way an enterprise system would be — with every architectural decision
explained and measured, not assumed.

Secondary objective: produce a portfolio-quality case study and a base of hands-on experience for
AI Architect / AI Platform Architect / AI Engineering Lead interviews.

## 4. Target Users (for this project's design, not real deployment)

- **Primary persona:** an internal advisor/case worker who reviews ranked recommendations for a
  candidate or a job and needs an explanation they can act on or relay to the candidate/employer.
- **Secondary persona:** a platform operator/engineer who deploys, monitors, and maintains the
  system.
- Out of scope for v1: self-service candidate-facing portal, public API, anonymous access.

## 5. Use Cases (v1 scope)

| ID | Use case | Summary |
|---|---|---|
| A | Candidate → Job matching | Given a candidate, return ranked jobs with score, matching/missing skills, qualification/location/salary compatibility, explanation |
| B | Job → Candidate matching | Given a job posting, return ranked candidates with the same supporting evidence, inverse direction |
| C | Free-text skill extraction | Given raw job description text, extract and normalize skills into a canonical taxonomy (rules/dictionary first) |
| D | Skill-gap analysis | Compare candidate skills vs. job/occupation requirements; distinguish "not recorded" from "assessed and absent" |
| E | Learning/course recommendations | Recommend courses that close identified skill gaps, starting with a transparent rule-based baseline |
| F | Similarity / semantic search | Similar jobs, similar candidates (non-sensitive attributes only), similar courses, fuzzy title/skill matching |

Each use case must ship with: an explanation of *why* a result was produced, and a documented set
of known limitations.

## 6. Scope Boundaries (v1)

**In scope:**
- Deterministic rule-based matching as the baseline for every use case, evaluated before any
  ML/embedding approach is introduced.
- FastAPI service exposing precomputed recommendations.
- Docker Compose deployment, Postgres as system of record.
- Synthetic data generation with deliberate imperfections (duplicates, synonyms, missing fields).
- Local-first development; cloud deployment (Azure) deferred/optional, decided at Phase 11.

**Out of scope for v1 (explicitly deferred):**
- Public self-service portal or anonymous access.
- Complex multi-agent orchestration frameworks.
- Kubernetes (introduced only after Docker Compose deployment is stable — Phase 12).
- Large-scale collaborative-filtering recommenders (only introduced if synthetic interaction data
  is sufficient and a rule-based baseline is insufficient).
- Any real candidate PII — all data synthetic.

## 7. Non-Functional Requirements

| Category | Requirement (v1 target) | Validation method |
|---|---|---|
| Performance | API request-time compute bounded; recommendations served from precomputed data where possible | Load testing, Phase 9 |
| Explainability | Every match/recommendation includes a human-readable rationale, not just a score | Manual + evaluation review, Phase 4 |
| Security | Secrets never committed to source; authN/authZ on all non-health endpoints before Phase 6 ships | Code review, dependency/image scanning, Phase 8 |
| Observability | CPU/RAM/latency/error-rate/batch-time measurable via Prometheus+Grafana | Phase 9 |
| Reproducibility | Synthetic dataset and scoring results reproducible from a fixed seed | Re-run and diff, Phase 2+ |
| Portability | Runs identically from a clean checkout via Docker Compose; disconnected deployment validated | Phase 7, Phase 10 |
| Resource constraints | Must run within measured dev-machine limits: 16GB RAM, 8GB VRAM, 8c/16t CPU (see `docs/hardware-inventory.md`) | Ongoing, Phase 9 sizing |

## 8. Data Approach

- Entities: candidates, candidate skills, job postings, job requirements, occupations, skill
  taxonomy, courses, certifications, course-to-skill mappings, optional synthetic interactions.
- Generation is deterministic (fixed seed), with intentional data-quality issues so the matching
  system has real signal to work with (not a trivial dataset).
- Full schema and generation methodology documented separately in `docs/data-model.md` (Phase 2
  deliverable).
