# Ingress and Identity (Load Balancer, Reverse Proxy, API Gateway, SSO)

Status: v1 implemented and verified end-to-end against the real running stack.

Level-3 diagram (cropped from the master Technical Architecture diagram): [`ingress-and-identity.drawio`](ingress-and-identity.drawio).

This is everything between a real user's browser and the rest of the platform: how a
request physically gets in (Load Balancer, Reverse Proxy, API Gateway) and how a human
logs in (Keycloak SSO). Two previously separate docs (`ingress-layer.md`, `sso.md`) are
merged here because they're really one story: "how does a request, and the person
behind it, get into this system."

## Part 1 : Load Balancer, Reverse Proxy, API Gateway

### Purpose & Scope

Running local ingress chain flow (`Candidate -> Load Balancer -> Reverse Proxy -> App Frontend -> API Gateway -> {matching_api, extraction_api}`) is something you can actually curl and click through.

Out of scope, by design: TLS (no real certificate, see [security-and-threat-model.md](../security-and-threat-model.md)), JWT/auth validation at the Gateway (SSO is a separate Frontend-tier login gate, see Part 2 below, not a Gateway concern here), and a cloud-managed Load Balancer (this project avoids any real Azure dependency, assumption A1 in [assumptions-register.md](../assumptions-register.md); see [ADR 0002](../adr/0002-build-the-ingress-layer.md) for why Load Balancer is nginx too, not a cloud service, even though that's the more realistic production shape).

### Architecture & Design

Three official `nginx:1.27-alpine` containers, no custom Dockerfile, configured via mounted `:ro` config files, the same convention as `docker/prometheus/prometheus.yml`:

- Reverse Proxy (`docker/nginx-reverse-proxy/nginx.conf`) fronts `frontend` only (the TLS-termination point in a real deployment; websocket `Upgrade`/`Connection` headers are forwarded, required for Streamlit's live UI updates). Two identical replicas, `reverseproxy-1`/`-2`, not published to the host.
- Load Balancer (`docker/nginx-load-balancer/nginx.conf`) round-robins across the two Reverse Proxy replicas (nginx's default algorithm, no directive needed). It is the only publicly reachable ingress component, published at `8080`. It adds an `X-Upstream` response header so round-robin is independently verifiable rather than assumed.
- API Gateway (`docker/nginx-gateway/nginx.conf`) does path-based routing between App Frontend and the backend APIs it calls: `/matching/* -> api:8000/*`, `/extraction/* -> extraction:8002/*` (prefix stripped by the trailing slash on both `location` and `proxy_pass`, so `api`/`extraction` see identical paths to before, no changes needed in those services). Not meant to be public-facing, but published at `8099` anyway for direct debugging, matching this repo's existing habit of publishing every port.

Why only Load Balancer is published to the host: every other service in this repo publishes its port for local debugging convenience. This layer deliberately breaks that habit for Reverse Proxy/Gateway, the entire point of an ingress chain is a single public entry point; publishing every internal hop too would defeat the demonstration.

### Implementation

`docker-compose.yml`: four services (`gateway`, `reverseproxy-1`, `reverseproxy-2`, `loadbalancer`), each with a healthcheck (`wget` against `127.0.0.1`, not `localhost`, see Known Limitations). `frontend`'s `API_URL`/`EXTRACTION_URL` default to `http://gateway/matching`/`http://gateway/extraction` instead of calling `api`/`extraction` directly (`app/frontend/streamlit_app.py`), and `frontend` depends on `gateway` being healthy.

### Verification & Results

All verified against the real running containers, not assumed from config alone:

- Round-robin: 5 sequential `curl http://localhost:8080/` calls, `X-Upstream` alternated between the two `reverseproxy-1`/`reverseproxy-2` container IPs (172.21.0.10 / 172.21.0.11), confirming real load distribution, not just that nginx accepted the config.
- Gateway routing is transparent: `curl http://localhost:8099/matching/candidates/1/job-matches` returned the exact same response (real ranked match data, after running `migrate`/`seed`) as calling `api:8000` directly confirming the prefix-strip routing works and `api` is unaware it's being proxied.
- Websocket passthrough through the full chain: a raw HTTP/1.1 Upgrade handshake (`Connection: Upgrade`, `Upgrade: websocket`) sent to `http://localhost:8080/_stcore/stream` returned `101 Switching Protocols` confirms Load Balancer to Reverse Proxy to Frontend preserves the websocket upgrade end to end, not just plain HTTP GETs. Page title (`<title>Streamlit</title>`) also confirmed rendering through the full chain.
- A real bug found and fixed during verification: the `gateway`/`reverseproxy`/`loadbalancer` healthchecks initially used `http://localhost/...`, which failed with "connection refused" Alpine's `wget` resolves `localhost` to `::1` first, but nginx (as configured here) only binds `0.0.0.0:80` (IPv4), not `[::]:80`. Fixed by healthchecking `127.0.0.1` explicitly instead of `localhost`.

### Known Limitations

- No TLS ; Reverse Proxy terminates connections in plaintext. The real TLS-termination responsibility this component would have in production isn't exercised here (see [security-and-threat-model.md](../security-and-threat-model.md)).
- No JWT/auth validation at the Gateway, it's pure routing, no rate limiting or token checks of its own (the APIs' existing `JME_API_KEY` check and Redis-backed rate limiting, documented in [security-and-threat-model.md](../security-and-threat-model.md) and [data-platform/redis-infrastructure.md](data-platform/redis-infrastructure.md), are unchanged and still the only enforcement).
- Load Balancer is nginx, not a cloud-managed service, an intentional choice given this project's no-real-Azure-subscription constraint (assumption A1), not a claim that this is how a real deployment's Load Balancer would be built (see [ADR 0002](../adr/0002-build-the-ingress-layer.md)).
- Gateway/Reverse Proxy healthchecks use IPv4-only `127.0.0.1` rather than fixing nginx to also bind `[::]`/dual-stack, sufficient for this project's local-only scope.

### Roadmap

- JWT validation at the Gateway (rejecting unauthenticated requests before they reach `api`/`extraction`) once the SSO tokens below are something the Gateway could plausibly check, not built yet, see Part 2's Known Limitations.
- A real TLS certificate at the Reverse Proxy (even a self-signed one) if this project ever needs to demonstrate HTTPS locally.

## Part 2 : SSO / Identity (Keycloak)

### Purpose & Scope

`docs/architect/JME_Technical_Architecture.drawio` drew `App Frontend -> SSO` as a "documented, not provisioned" future login hop. This phase built it for real: a Keycloak container with a pre-seeded realm, and a real login/registration gate in front of the demo UI. Both login and registration render as inline forms on the app's own page today (see Implementation); there is no redirect to a separate Keycloak-hosted page anywhere in this flow.

This is a human/browser login gate only. `JME_API_KEY` (the header every API caller, including `frontend` itself, server-side, already attaches) is completely unchanged; it's still what `api`/`analytics`/`extraction` check for every request. SSO governs whether a human can see the Frontend UI at all; it does not replace or touch the existing service-to-service auth. See assumption A9 in [assumptions-register.md](../assumptions-register.md).

Out of scope, by design: JWT validation at the API Gateway (see Part 1's Roadmap), PKCE, token refresh, and a hardened session mechanism (see Known Limitations), all deliberately deferred for a local demo whose job is to show the login flow works, not to be production auth infrastructure. Self-service registration with a real `candidate`/`employer` realm role (issue #14, see Implementation) closes part of what was previously "role-based access control, deferred" — identity now carries a real role claim, but no backend service enforces it; see Known Limitations.

### Architecture & Design

Keycloak in dev mode, realm pre-seeded via `--import-realm` (`docker/keycloak/jme-realm.json`), no manual admin-console setup needed to run the demo. The realm defines a public client (`jme-frontend`, no secret standard for a browser-based SPA/public client, `directAccessGrantsEnabled: true` so it can do a Resource Owner Password grant), two realm roles (`candidate`/`employer`), two seeded test users already assigned one of those roles (`candidate`/`employer`, passwords in the realm file, clearly local-dev-only), and a second, confidential client (`jme-admin`, service account only, no login flows of its own) used to create new users and assign roles — least-privilege (`manage-users`, `view-users`, `view-realm` on the built-in `realm-management` client), not the Keycloak master admin bootstrap credentials.

One issuer URL now, not two: both the inline login form's token exchange and the inline registration form's Admin API calls happen server-side, inside the Frontend container, so both only ever need the internal Docker network address (`http://keycloak:8080/realms/jme`, `OIDC_INTERNAL_ISSUER`) — there's no browser-side redirect to Keycloak left that would need the host-published `:8180` URL.

Hand-rolled with `requests`, not `authlib`: this project's existing convention for calling another service is a module-level `os.environ.get("X_URL", "http://...")` plus plain `requests` calls (`app/api/analytics_client.py`, `app/frontend/streamlit_app.py`'s existing `API_URL`/`EXTRACTION_URL`), not a framework. `authlib` (and most other OIDC client libraries) assume a browser-redirect-based flow; this app doesn't have one anymore.

### Implementation

`app/frontend/streamlit_app.py`'s `_require_login()` — both login and registration are inline forms, no redirect to a separate Keycloak-hosted page for either:

1. If `st.session_state["id_token_claims"]` already exists, return immediately (already logged in).
2. Otherwise, show two sections under the page heading:
   - **"Log in"**: `st.text_input` username/password fields and a "Log in" button. Submitting calls `oidc.py`'s `password_grant_login(username, password)` (a Resource Owner Password grant directly against Keycloak's token endpoint); on success, decodes the returned `id_token`'s JWT payload (no signature verification local demo only, see Known Limitations) into `session_state`, then `st.rerun()`.
   - **"New here?"**: `st.text_input` full name/email/password fields and a "Register" button. Submitting calls `keycloak_admin.py`'s `get_admin_token()` then `create_user(email, full_name, password, admin_token)` (a direct `POST` to Keycloak's Admin API, username set to the email address), then immediately `password_grant_login(email, password)` to log the brand-new account straight in the same way login does, storing the entered name in `session_state["pending_full_name"]` so the profile form below can pre-fill it.
3. `st.stop()` either way nothing else in the app runs until one of the two forms resolves.

Role selection happens in the app itself, on first login, via `_require_profile()` (issue #15/#16):

1. Calls `app/frontend/profile_client.py`'s `get_profile(sub)` against the app's own `user_profiles` table. If found, returns its `role` immediately.
2. Otherwise (brand-new user, first login after registering), shows a one-time form: name (pre-filled from the registration form above, if this is that same session), a `candidate`/`employer` radio button, and a company-name field shown only for Employer.
3. On submit, calls `app/frontend/keycloak_admin.py`'s `get_admin_token()` and `assign_realm_role(sub, chosen_role, admin_token)` (`sub` is the ID token's own Keycloak user UUID, no separate username lookup needed) so the realm-role claim stays available for any future backend-enforced authorization, then `profile_client.create_profile(...)` to persist the profile row, which becomes the UI's actual source of truth for role from then on.

`docker-compose.yml`: a `keycloak` service (official `quay.io/keycloak/keycloak:26.0`, no custom Dockerfile), `frontend` depends on it being healthy and gets `OIDC_*` env vars plus `KEYCLOAK_ADMIN_CLIENT_ID`/`KEYCLOAK_ADMIN_CLIENT_SECRET` for the `jme-admin` service account. `docker/keycloak/jme-realm.json` is the entire realm definition `sslRequired: "none"` is set deliberately (see Known Limitations: no TLS anywhere in this stack yet, and Keycloak would otherwise require HTTPS for the container-to-container token-exchange call, which isn't `localhost` from Keycloak's perspective). `jme-frontend` also carries a protocol mapper (`oidc-usermodel-realm-role-mapper`) so `realm_access.roles` lands in the **ID token**, not just the access token Keycloak's default `roles` client scope only puts it on the access token, which the frontend never sees otherwise.

A real, non-obvious finding from building this: Keycloak v26's realm-import does **not** resolve `${env.VAR}`-style placeholders in a client's `secret` field (tried first, silently left the literal string in place, `get_admin_token()` got a `401`). The `jme-admin` client secret is therefore a plain hardcoded dev-only value in `jme-realm.json`, same convention as the seeded users' passwords in that same file it must match `KEYCLOAK_ADMIN_CLIENT_SECRET` in `.env`, which the Frontend container actually reads.

**Issue #15 (backend half of a two-issue split, see issue #16 for the frontend half)**: Keycloak and `assign_realm_role()` are identity-only — nothing about *who* a user is (name, contact info) is ever written to this app's own database. A new standalone `app/identity/models.py::UserProfile` table (`keycloak_user_id` unique, `role`, `full_name`, `email`, `company_name` nullable) and a new `app/api/profile_routes.py` (`POST /profiles`, `GET /profiles/{keycloak_user_id}`, both behind the same `RequireApiKey` dependency as every other route, no new auth mechanism) now give the app a real place to persist that. At the time, there was deliberately no FK to `candidates`/`jobs` — linking a profile to a specific candidate/job *record* was separate, undone work; issue #17 (below) closed that gap for the candidate side.

**Issue #16 (frontend half)**: `_require_role()` is replaced by `_require_profile()` as described above (`app/frontend/profile_client.py` is the new module). The logged-out screen also has explicit `### Log in` / `### New here?` section headings.

**Issue #17 (real per-user `candidate_id`)**: `app/frontend/streamlit_app.py` originally hardcoded `candidate_id = 1` for every candidate — every candidate shared one `candidates` row from the seeded synthetic dataset, so one candidate's CV upload was visible to (and overwritten by) every other candidate. `UserProfile` now carries a nullable `candidate_id` FK to `candidates.id` (new migration), and `POST /profiles`'s `create_profile()` (`app/api/profile_routes.py::_get_or_create_candidate`) creates a brand-new, real `app.ingestion.source_models.Candidate` row for `role=candidate` registrations, using the registration form's `full_name`/`email` — `location_city`/`location_region`/`years_experience` are required by that model but not collected by this form yet, so MVP placeholders (`"Unknown"`/`"Unknown"`/`0`) are used (see `docs/architecture/frontend.md` Known Limitations). If `Candidate.email` collides (the `unique=True` constraint, e.g. re-registration, or an overlap with a seeded synthetic email), the existing `Candidate` is reused by email lookup instead of failing registration. Employer profiles are unaffected — `candidate_id` stays `NULL`, there's still no `employers` table to link to. The frontend then reads `candidate_id` straight from `st.session_state["profile"]` instead of the old hardcoded `1`.

**Login/registration UX follow-ups (after issue #16)**: two rounds of changes moved this entirely away from Keycloak's own hosted pages. First, the "Log in" link (which redirected to Keycloak's hosted login page in a new browser tab Streamlit renders markdown links with `target="_blank"`) was replaced with the inline username/password form described above a separate window felt disconnected from "one app." Then the "Register" link (same redirect pattern, to Keycloak's hosted registration form) was replaced the same way: an inline full-name/email/password form that calls Keycloak's Admin API directly (`create_user`) instead of redirecting. With both flows now inline, the Authorization Code dance (`?code=&state=` callback handling, CSRF `state` tracking, `exchange_code_for_token`, `build_auth_url`/`build_registration_url`) became entirely dead code and was deleted; `oidc.py` now holds only `password_grant_login` and `decode_id_token`. `jme-realm.json`'s `registrationAllowed: true` is now unused (nothing links to Keycloak's hosted registration form anymore) but left in place since it's harmless and still accurate as "this realm permits registration," just via the Admin API instead of Keycloak's own UI.

### Verification & Results

Verified with real scripted HTTP sessions against the real running stack, not browser screenshots nor mocks, hitting real Keycloak/API endpoints directly:

1. `streamlit.testing.v1.AppTest` (`tests/frontend/test_streamlit_app.py`): an unauthenticated session sees both inline forms (login's username/password fields and a "Log in" button; registration's full-name/email/password fields and a "Register" button) and never reaches the profile form; submitting valid/invalid login credentials (mocked token endpoint) logs in or shows an error respectively; submitting the registration form (mocked `create_user`/token endpoint) creates the account, logs in, and pre-fills the following profile form's name field from what was just entered; a duplicate-email registration shows the "already exists" error; a session with `id_token_claims` pre-seeded sees the real app and a "Log out (username)" button; clicking logout clears the session and shows both forms again.
2. Login's Resource Owner Password grant, verified directly against the live Keycloak container, not mocked: `POST /protocol/openid-connect/token` with `grant_type=password` and the seeded `candidate` user's real credentials returns a real `id_token`; the same request with a wrong password returns `401` — confirming `password_grant_login()`'s both branches (success and the `ValueError` it raises) against the real stack.
3. Registration's Admin-API user creation, verified directly against the live Keycloak container with a throwaway account (cleaned up after): `get_admin_token()` succeeds against the real `jme-admin` service account; `POST /admin/realms/jme/users` with a brand-new email returns `201` and a `Location` header `create_user()` parses for the new user id; the identical request again returns `409` (the duplicate-email case `create_user()` turns into its `ValueError`); a `password_grant_login()` immediately afterward, with the just-registered credentials, succeeds the exact sequence `_require_login()`'s Register button drives.
4. Registration + role assignment (issue #14's realm-role mechanics, still used by `_require_profile()`), verified against the real running stack: the seeded `candidate` user's ID token decodes to include `"realm_access": {"roles": ["candidate"]}` (confirmed via a real password-grant token exchange against the live Keycloak container) proving the protocol mapper works. A full create-user -> `assign_realm_role()` -> re-check round trip against the live Admin API confirmed the role is actually persisted (`role-mappings/realm` listed it afterward), not just a 2xx response.
5. Profile capture (issues #15/#16), verified end-to-end against the real running stack with a scripted session: registered a brand-new user, logged in, confirmed `GET /profiles/{sub}` returned `404` (no profile yet, so `_require_profile()` would show the one-time form), submitted the form's equivalent (`POST /profiles` with role `candidate`), then confirmed `GET /profiles/{sub}` returned `200` with the persisted role — the exact round trip `_require_profile()` drives, not mocked. The test user and its `user_profiles` row were cleaned up after. `tests/api/test_profile_routes.py` (4 tests), `tests/frontend/test_profile_client.py` (3 tests), and `tests/frontend/test_streamlit_app.py`'s profile-form tests (new-user-sees-form, submit-as-candidate, submit-as-employer-with-company-name) cover the pure logic headlessly.
6. Per-user `candidate_id` (issue #17), verified live against the real running stack: registered two distinct brand-new Candidates and confirmed each got their own, different `candidate_id` (real new `candidates` rows, not the seeded dataset's `candidate_id=1`); uploaded a CV to the first candidate's own id and confirmed the second candidate's `GET /candidates/{id}/cv` still returned `404`, not the first candidate's CV — proving the isolation is real, not just two different ids that both happen to work; confirmed an Employer registration left `candidate_id` `NULL`. All test rows (both `user_profiles` and `candidates`) and the Keycloak users were cleaned up after.

7. **Issue #26** (real JWT verification + ownership enforcement): verified live against the real running stack using throwaway Keycloak users created via the Admin API (never the real end-user accounts, cleaned up after) — a request with no `Authorization` header `401`s before any network call; a candidate can read/edit their own `candidate_id`'s details but a second candidate gets `403` on both; a seeded/unowned candidate (no linked `UserProfile`) stays freely readable by any authenticated caller; an employer can edit their own job but a second employer gets `403`; any candidate can view any job's details regardless of who posted it (job postings are meant to be public, unlike candidate details); applying/saving a job and reading job-interactions/audit history are all rejected (`403`) for a caller who isn't the record's real owner; a seeded/unowned job stays freely matchable; a real `refresh_token` grant against the live Keycloak container produces a working new access token. `tests/api/test_jwt_auth.py` covers the signature-verification logic itself against a throwaway RSA keypair (valid/expired/wrong-issuer/wrong-client/untrusted-signer/missing-header cases); every DB-backed route test overrides `get_verified_claims` the same way they already override `get_db`.

(Historical note: an earlier version of this flow redirected to Keycloak's own hosted login/registration pages via the Authorization Code grant, which surfaced a real RFC 6265 finding — an HTTP client that strictly follows the spec refuses to send a `Secure`-flagged cookie back over plain HTTP, while real browsers treat `http://localhost` as a "potentially trustworthy" secure context and send it anyway. That code path no longer exists see the Login/registration UX follow-ups in Implementation so this no longer applies to this app, but is worth remembering if a redirect-based flow is ever reintroduced here or elsewhere against a non-TLS Keycloak.)

### Known Limitations

- `st.session_state` is not a hardened session mechanism, it's per Streamlit server connection, not a signed/encrypted cookie-based session a real auth system would use. Acceptable for a local single-user demo, not for anything deployed (same class of gap as `JME_API_KEY`, assumption A9).
- No **ID token** signature verification — `decode_id_token`'s payload is still base64-decoded and trusted as-is, used only for display claims (username, name, email) shown in the UI, never for authorization. This is now a narrower gap than it used to be: issue #26 added real signature verification on the separate **access token** (the one actually sent on every backend call, see below) — the ID token remains unverified because nothing security-sensitive is ever decided from it.
- Both login and registration use direct server-side calls to Keycloak (a Resource Owner Password grant and the Admin API, respectively) instead of a redirect-based Authorization Code flow: the Streamlit app itself collects and transmits the raw password, rather than Keycloak's own hosted page handling it and the app never seeing it (the standard OAuth2 advice for browser apps). Chosen deliberately so both forms render inline under the app's own heading instead of a separate browser tab/window; acceptable for a local demo over a trusted internal Docker network, not a pattern to carry into anything handling real user credentials at scale. PKCE and the CSRF `state` parameter are moot consequences of this — there's no redirect left for either to protect.
- No TLS anywhere (`sslRequired: "none"` on the realm), see Part 1 and [security-and-threat-model.md](../security-and-threat-model.md).
- No JWT validation at the API **Gateway** specifically — issue #26 added real verification at the `api` service itself (`app/api/jwt_auth.py`), not the Gateway layer, so a request that somehow reached `api` directly (bypassing the Gateway) would still be checked, but the Gateway itself still just routes without inspecting tokens. See Part 1's Roadmap.
- The `candidate`/`employer` role (sourced from the `user_profiles` table, issue #16) is still a pure Frontend-side UI distinction — `api` doesn't check *role* (e.g. "is this caller actually an employer") anywhere, only *ownership* (issue #26: "does this caller own this specific candidate/job record"). A candidate's verified identity can't be used to edit someone else's data, but nothing stops a candidate's token from being presented to an employer-shaped endpoint if it somehow had a matching owned record — acceptable since the UI never constructs that scenario, a real deployment would want role-based route guards too.
- Registration has no email verification and no rate limiting of its own now that it bypasses Keycloak's own hosted form (which had Keycloak's dev-mode defaults); fine for a local demo, not for anything exposed beyond one machine.
- The one-time profile form's `assign_realm_role()`/`create_profile()` calls, and the registration form's `create_user()`/`password_grant_login()` calls, have no retry/rollback if one succeeds and a later one fails; a user would just see a Streamlit exception and could retry by refreshing, not a graceful in-app error message or partial-state cleanup (e.g. a Keycloak user created but never logged into or profiled).
- **Closed (issue #26)**: `POST /profiles` (and every other identity-bearing route) no longer trusts a frontend-supplied `keycloak_user_id` at all — identity comes only from `app/api/jwt_auth.py`'s verified access-token `sub` claim, checked via Keycloak's JWKS/RS256 signature, issuer, and `azp` (authorized party). See `docs/architecture/frontend.md`'s issue #26 writeup for the full design (ownership enforcement, silent token refresh) and live verification.

### Roadmap

- **Done (issue #26)**: real signature verification against Keycloak's JWKS endpoint, plus ownership enforcement on every candidate/job-details/audit route — see `docs/architecture/frontend.md`.
- If this ever needs to defend against a more realistic threat model: move back to the redirect-based Authorization Code flow with PKCE for both login and registration, so the app itself stops handling raw passwords — the inline forms built here deliberately traded that off for a simpler, same-page UX in a local demo with a trusted internal network.
- JWT validation at the API **Gateway** layer itself (today it's at `api` directly, issue #26) would add defense-in-depth for a multi-service deployment, and role-based (not just ownership-based) route guards would close the "candidate token presented to an employer-shaped endpoint" gap noted above — neither is built, no concrete need yet for a single-developer demo.

## Resource Footprint and Scaling

All three nginx containers and Keycloak are lightweight relative to everything behind them `docker stats` shows nginx idling at single-digit MB each (see [operations/infrastructure-sizing.md](../operations/infrastructure-sizing.md) for the full per-service table). nginx is also stateless request routing with no per-request compute of its own, so this layer is not where concurrent-user capacity is actually won or lost: the real ceiling is whatever sits behind the Gateway (see [application-services/README.md](application-services/README.md) and [ai-ml-and-mlops.md](ai-ml-and-mlops.md)). Scaling this layer, if it were ever needed, is the standard nginx pattern: add more Reverse Proxy replicas behind the Load Balancer (already 2 today) and/or more Gateway instances behind a second small load balancer, nothing architecturally new, unlike the application/AI layers below. Keycloak in dev mode is single-instance with no HA story; a real deployment would run it clustered against a shared database, not built here (local-only scope, same as every other single-instance service in this project).

See [operations/capacity-planning.md](../operations/capacity-planning.md) for the full worked concurrent-user scenario across every layer.
