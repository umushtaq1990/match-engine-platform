# Free-Text Skill Extraction: Use Case C

## Purpose & Scope

Extract both **technical and non-technical** skills from free text (a job description, a CV snippet) and classify each as **required** or **preferred**, canonicalized onto this project's existing 64-skill taxonomy (`Skill`/`SkillSynonym`) not just technical keywords. The taxonomy already spans both (`programming`/`data`/`cloud`/`ai`/`it`/`engineering` alongside `soft_skill`/`business`/`hr`/`healthcare`/`trades`/`logistics`/`creative`/`finance`/`office`/`education`), so the extraction prompt and evaluation must treat both as first-class, not add non-technical as an afterthought.

Per assumption A5b, this use case specifically skips a rule-based baseline and goes straight to an NLP/embedding-based approach, the opposite of every other use case in this project, and the reason the shared LLM/embedding serving layer (`docs/architecture/ai-ml-and-mlops.md`) was stood up before this work could start.

Out of scope (v1/v2): negation handling, raw-CV-text ingestion, and wiring extraction into a real write path that populates `JobSkill`/`CandidateSkill` rows, see Known Limitations and Roadmap.

## Architecture & Design

**Why a hybrid pipeline (LLM extraction + embedding canonicalization), not either alone.** `SkillSynonym`'s own docstring (`app/ingestion/source_models.py`) was written anticipating "a dictionary-based extractor" — a simpler design than what A5b later committed to. The hybrid pipeline below still uses `SkillSynonym`, just differently: not as a lookup dictionary, but as extra reference text that improves embedding-based canonicalization.

- **LLM-only** (forced to pick from the 64-skill list in-prompt) tends to force a match even when the text doesn't really mention anything in the taxonomy, you lose the "this is a real skill mention the taxonomy doesn't cover" signal, which matters for taxonomy maintenance.
- **Embeddings-only** (no LLM) means hand-building a phrase-chunking/NER step first, reinventing what a small instruct model already does adequately for this volume of text.
- **Hybrid**: the LLM extracts candidate skill phrases + a required/preferred guess; embedding similarity against the canonical skill set (names *and* synonyms) then maps each phrase to a `skill_id` with a **quantifiable confidence score** (cosine similarity) a measurable, tunable threshold, the same discipline already used for data-quality check thresholds, not a black-box "trust the LLM" call.

**Service boundary**:

| | Decision | Rationale |
|---|---|---|
| Service | New `extraction` service, own image (`docker/Dockerfile.extraction`) | Separately testable/evaluable, same bounded-context pattern as `analytics` |
| Model access | Calls the existing `ollama` service over HTTP, no model weights in this image | Reuses the shared serving layer; this service is pure orchestration logic |
| DB schema | **Public schema** (not an isolated schema like `analytics`) | Unlike behavioral analytics (a genuinely separate concern), this service's eventual purpose (v3) is to populate the *same* `job_skills`/`candidate_skills` tables the matching engine already owns, it's part of the core domain, not an adjacent one. Its eval tables join the same migration history as `evaluation_runs`/`data_quality_runs` |
| Error handling | Failures surface as real errors to the caller, **not** swallowed like the analytics instrumentation hook | Analytics impressions are optional side-effects; here, the caller usually has nothing useful without a result (same distinction flagged in `docs/architecture/ai-ml-and-mlops.md`'s consumer-pattern section) |

**Golden dataset (ground truth)**, two complementary parts, not one:

- **Part A generator-injected** (`app/ingestion/generate_synthetic_data.py`, enhanced): job description text originally was unrelated filler (`fake.paragraph(...)`), it didn't mention the job's actual skills at all. Enhanced to weave the job's real required/preferred skills into the description prose, **sometimes by canonical name, sometimes by a synonym**, so it isn't trivially easy. Ground truth = the `JobSkill` rows already generated for that job, cheap, deterministic, scales to all 1,000 jobs for free. This is *not* a repeat of the matching-evaluation circularity mistake (`docs/architecture/ai-ml-and-mlops.md`): there, the risk was grading the ranking formula against labels derived from that same formula. Here, the task is literally "parse this text and recover the structured facts it contains", the text is *constructed from* the ground truth by design, which is the correct way to test a parser, not a methodological error. It proves mechanical correctness (can the pipeline recover known facts from text), not real-world recall.
- **Part B hand-authored, harder cases** (`data/golden/skill_extraction.yaml`, checked into git): a few dozen realistic snippets, job description and CV-style text, specifically covering what Part A's templates can't exercise: skills mentioned only via an uncommon synonym or paraphrase, ambiguous requirement language ("exposure to X is a plus" vs. "must have X"), non-technical skills stated in prose rather than a bulleted list, and mentions of real-sounding skills **not in the taxonomy at all** (tests the "no match" path, not just the match path). Hand-authored because this is exactly the part a template generator structurally cannot produce, real ambiguity and phrasing variety. Stored as a versioned fixture file, not a DB table, so changes are git-reviewable like any other test fixture.

**Metrics**, different in kind from the matching-ranking metrics (which measure *ranking* quality, not *extraction* accuracy):

| Metric | What it measures |
|---|---|
| Skill-set Precision / Recall / F1 | Set comparison per example: predicted `skill_id`s vs. expected `skill_id`s, micro-averaged across all golden examples |
| Requirement-level accuracy | Of the correctly-identified skills (true positives only), what fraction got required/preferred right |
| Unmatched-phrase rate | How often a real extracted phrase falls below the canonicalization threshold, not an error by itself, but worth tracking per model/threshold config |

**Results storage** (mirrors the matching-evaluation pattern exactly): MLflow (existing service, new experiment) tracks run-level params (`llm_model`, `embedding_model`, `similarity_threshold`, `prompt_version`) and the three metrics above. Postgres (`extraction_runs` /`extraction_example_results`, same two-level shape as `evaluation_runs`/`data_quality_runs`) keeps per-example predicted-vs-expected detail, for drill-down into exactly which examples a given config got wrong.

## Implementation

**Pipeline**:
1. **LLM extraction**: an instruct model via Ollama's `/api/generate`, given the raw text, returns a JSON list of `{phrase, requirement_level_guess}`. Prompt explicitly asks for *all* skill mentions, technical and non-technical, not just an obvious technical subset.
2. **Embedding canonicalization**: an embedding model via `/api/embeddings`. Canonical skill names + all `SkillSynonym` rows are embedded **once** (cached, not recomputed per request, 64 skills plus synonyms is a small, static set). Each extracted phrase is embedded and compared by cosine similarity against that cached set; best match above a threshold → that `skill_id`. Below threshold → recorded as "no taxonomy match," not silently dropped.
3. **Output**: a list of `{skill_id, requirement_level, confidence, source_phrase}` plus a separate list of unmatched phrases.

Both the LLM model and the embedding model are **run parameters passed through to Ollama's API**, not hardcoded, swapping models is a different MLflow run, not a code change. That's what makes "try different models, see what scores better" actually work.

### CV upload storage

A candidate can upload their CV as a PDF (`POST /candidates/{id}/cv`, `GET /candidates/{id}/cv` for metadata, `GET /candidates/{id}/cv/download` for the file itself), a genuinely basic feature by design: PDF only, 2MB cap, one CV per candidate (a re-upload overwrites the prior one, no version history), no virus scanning. The point was answering "where does a real candidate's uploaded document live," not building a document-management system.

**Tool choice, verified not assumed**: SeaweedFS, not MinIO. MinIO stopped publishing public container images in 2025 confirmed from a changelog: `docker pull minio/minio` returns "pull access denied, repository does not exist," and both Docker Hub's and Quay's tag-listing APIs refuse unauthenticated access for that repository. SeaweedFS's `chrislusf/seaweedfs` image is still freely pullable (confirmed: `docker pull chrislusf/seaweedfs:4.51` succeeds), open source, and speaks the same S3-compatible API any client library already expects the `minio` Python package (an S3 client despite its name) works against it unmodified, confirmed by a real upload/download round trip before any application code was written. Runs in `mini` mode (bundles master/volume/filer/S3 gateway in one process), appropriate at this project's scale (50-100 CVs) rather than a distributed storage cluster.

Only object *metadata* (`CandidateDocument`: candidate_id, object key, filename, content type, size, upload timestamp) lives in Postgres, the PDF bytes themselves live only in object storage, never duplicated into the relational database. Validation checks both the declared Content-Type
*and* the actual PDF magic bytes (`%PDF-`), since a client can claim any content type it likes for a request body. Deliberately not fail-open like the Redis integrations elsewhere in this project, if object storage is unreachable, the upload fails with a real `503`, since a CV upload with nowhere to put the file is a genuine failure the caller must see, not something to silently drop.

### Synthetic CVs

`app/extraction/generate_synthetic_cvs.py` (`docker compose run --rm cv-seed`) closes a real gap: the synthetic dataset had 2,000 candidates but, before this, zero CV *documents* only the `generate_synthetic_data.py` relational rows existed, matching `data-model.md`'s stated scope.
For every seeded candidate without an existing `candidate_documents` row, it builds a one-page PDF (name/contact/location, a summary line from `years_experience` + `primary_occupation_id`, and the candidate's own `candidate_skills` rows) with `fpdf2`, then pushes it through the **exact same** `validate_cv_upload()` + `upload_cv()` path a real browser upload hits, the resulting `candidate_documents` rows and SeaweedFS objects are indistinguishable from genuine uploads, not a separate synthetic-only code path.

Idempotent by design: a candidate that already has a `candidate_documents` row, a real upload, or a prior run of this script is left untouched (`--force` overrides this). CI's smoke test exploits this directly: it uploads a real CV for candidate 1 first, then runs `cv-seed`, then asserts candidate 1's `original_filename` is still the uploaded one (`ci_test_cv.pdf`), not the synthetic generator's output, proving the generator never overwrites a real upload.

The generated PDF bytes are **never committed to this repository**, same stance as the rest of the synthetic dataset (`docs/progress.md`). Anyone who needs the CV documents runs `docker compose run --rm seed && docker compose run --rm cv-seed` themselves; the generator is fully deterministic in content (it reads straight from each candidate's already-seeded skills, not from randomness).

## Verification & Results

**Generator enhancement**: `app/ingestion/generate_synthetic_data.py` now weaves each job's actual required/preferred skills into its `description_raw` text, sometimes by canonical name and sometimes by a known synonym (confirmed: 311/1,000 jobs use a synonym variant, not just the canonical name). Verified against real rows, e.g. job #1's description mentions "Django, Cybersecurity, and Quality Assurance" as required and "PowerPoint" as preferred, exactly matching its real `JobSkill` rows, not a coincidence.

**A real bug found and fixed during the first eval run**: the first baseline run scored **F1 = 0.0385**, essentially nothing extracted. Root-caused (not guessed) by calling Ollama directly with the exact prompt: `"format": "json"` (the loose string) let `llama3.2:1b` emit a single malformed object (`{" phrase": "HR Coordinator 4", ...}`) instead of the requested array, which the parser correctly rejected as invalid (returning zero extracted phrases, not a crash). Fixed by passing an actual **JSON Schema** as `format` instead, Ollama then constrains the output structurally, not just to "valid JSON of any shape." Re-verified directly via `curl` before touching code: the schema form correctly extracted `Kubernetes`, `Nursing`, `Social Media` from the same text the loose string had failed on.

**Baseline run, post-fix** (`llama3.2:1b` + `nomic-embed-text`, threshold 0.55, prompt v2, 46 examples = 30 generator-injected + 16 hand-authored): **Precision 0.636, Recall 0.447, F1 0.504, requirement-level accuracy 0.961, unmatched-phrase rate 0.0** a real, unoptimized baseline. Logged to MLflow (`jme-skill-extraction` experiment) and Postgres (`extraction_runs`/`extraction_example_results`) for later comparison.

**Spot-checked per-example results, not just the aggregate**: the out-of-taxonomy hand-authored case (`astrophotography and vintage typewriter repair`) correctly produced zero matches, no false positive forced onto the taxonomy. A CV-style snippet mentioning a real skill (`Python`) alongside a deliberately absurd one (`underwater basket weaving`) correctly matched the former and flagged the latter as unmatched rather than forcing it onto the nearest taxonomy entry. Several examples scored a perfect 1.0 F1 (all skills recovered, all requirement levels correct); several scored 0 (the LLM returned an empty list for that text) a believable result for an unoptimized 1B parameter model, not a bug.

**Model/threshold tuning**:
- **Threshold sweep** (`llm_model=llama3.2:1b`, same prompt, 46 examples each): 0.45 → F1 0.479, 0.50 → F1 0.456, **0.55 (the original default) → F1 0.504, still the best of the five values tested**, 0.60 → F1 0.344, 0.65 → F1 0.412. The original choice held up under a real sweep rather than being revised on a hunch.
- **LLM comparison at that threshold**: `qwen2.5:1.5b` vs. the original baseline `llama3.2:1b`, **F1 0.60–0.66 vs. 0.504** across two separate runs (run-to-run variance from sampling, both comfortably above the baseline), recall improving most (0.60–0.68 vs. 0.447), requirement-level accuracy also slightly better (0.978–0.986 vs. 0.961). `qwen2.5:1.5b` is also smaller on disk (986MB vs. 1.3GB) despite having more parameters, a more efficient quantization, not a size/quality tradeoff in the usual direction.
- **Promoted**: `DEFAULT_LLM_MODEL` in `app/extraction/pipeline.py` is now `qwen2.5:1.5b`, a measured decision, not a default left unexamined. `llama3.2:1b` is no longer pulled by default (`docker-compose.yml`'s `ollama-pull` job) but remains reproducible on demand.
- Re-verified against the live `/extract` endpoint after promoting: correctly extracted all four skills (Python, Docker, Communication as required; Kubernetes as preferred) from a real request, with confidence scores all above 0.77 and zero unmatched phrases.

**Re-verification after the synthetic generator changed**: the generator later changed (domain-anchored skill sampling, see `docs/architecture/data-platform/data-at-scale.md`). Re-ran the exact same eval (`qwen2.5:1.5b`, threshold 0.55) against the new data: **F1 0.6766**, consistent with the 0.60–0.66 range measured above, confirming the tuned configuration still holds against the regenerated dataset.

**Stage-level traceability found and fixed a real accuracy ceiling (prompt v3, threshold 0.65).** Before this, only final predicted-vs-expected `skill_id` sets were persisted — enough to know a given run scored, say, F1 0.68-0.72, but not *why* a specific example failed: did the LLM genuinely miss a skill, or extract something reasonable that the embedding step then matched to the wrong taxonomy entry? New nullable JSONB columns on `extraction_example_results` (`extracted_phrases`, `match_detail`, `unmatched_detail`) plus MLflow tracing on `extract_skills()` (see `docs/architecture/ai-ml-and-mlops.md`'s tracing section) close that gap. Using it against real golden-dataset failures found the dominant error mode was **not** missing skills outright, it was the LLM extracting verbose, filler-laden fragments ("Adept at translating complex concepts into engaging content") that the embedding step then confidently (and wrongly) matched to an unrelated taxonomy entry ("passion for technology" → "Telekinesis", at a confidence score sitting right at the old 0.55 threshold boundary). Fixed on both ends: `PROMPT_VERSION` "v2"→"v3", explicitly instructing short canonical skill names and explicitly naming filler words to strip ("excellent", "strong", "proven", "passion for", "experience with") with negative examples; `DEFAULT_SIMILARITY_THRESHOLD` raised 0.55→0.65. Measured effect: F1 0.6847→0.7150 from the prompt change alone; the threshold raise on top was flat-to-marginal, confirming the prompt fix (not the threshold) was carrying the real improvement — exactly the kind of causal attribution stage-level traceability is for, instead of changing two things and guessing which one mattered.

A real API-format bug would have corrupted this comparison if not caught: Llama-3.2-3B-Instruct-AWQ initially scored near-zero (its first full run) because `app/golden/vllm_client.py` was calling `/v1/completions` (a bare prompt string) — Llama's instruction-tuned checkpoint needs the chat template applied via `/v1/chat/completions` to behave as an instruction-follower at all, confirmed directly with `curl` against both endpoints with the identical text (same 4 obvious skills: `/v1/completions` returned a bare `[ ]`, `/v1/chat/completions` correctly extracted all 4). Fixed the client to always use chat-completions and re-ran all three models for a fair comparison before drawing any conclusion from the numbers above.

**Bigger-model comparison, CPU-only (the vLLM/GPU path tops out around 3B-class models on this hardware's 8GB VRAM, see `docs/architecture/ai-ml-and-mlops.md`), targeted rather than brute-forced.** Re-running the full ~2,000-example dataset for every new model candidate is a 14-18+ hour CPU job per model (measured: ~82.5ms/token decode for a 1.5B model, extrapolated to ~390ms/token for 7B) — not worth paying for every size/family to test. Instead, queried the three already-measured runs above for the subset of examples where **all three** scored F1 < 0.5 (95 of ~2,000 examples, 4.75%) — the genuinely hard tail, not a random sample — and tested only that subset against `qwen2.5:7b` and `gemma2:9b` (both via Ollama, CPU, `--hard-cases-f1-below 0.5 --compare-run-ids <the three run ids>`), cutting the time cost by ~95% for the question that actually mattered: does a bigger model recover more of the cases the smaller ones already fail on.

**Reading these honestly, same discipline as the recommendation-evaluation numbers above**: the absolute F1 values here (~0.10-0.19) are much lower than the full-dataset numbers in the first table (~0.74-0.79) — expected and correct, not a regression, since this 95-example subset is *by construction* the hardest cases in the dataset (where all three smaller/GPU-served models already scored below 0.5), not a representative sample. The real finding is the relative trend: F1 improved monotonically with size/family across this hard subset (1.5B < 3B ≈ 3B < 7B < 9B), with Gemma2-9B the strongest of the five tested, about 13% better (relative) than Qwen2.5-7B and about 88% better than the weakest baseline on this same subset. Bigger genuinely helped on the cases that are actually hard; it just doesn't change the full-dataset picture materially, since the hard tail is only 4.75% of the data.

**Operational lesson from running this overnight, unattended**: CPU inference for 7B/9B models alongside the rest of the stack twice crashed Docker Desktop's engine under real memory pressure (not a slow response, `docker ps`/`docker version` returned literal `500` errors and every container exited) — diagnosed and recovered from autonomously, without human input, by raising the WSL2 memory ceiling and then, when that alone wasn't the real cause the second time, by trimming non-essential containers instead. Full story: `docs/operations/infrastructure-sizing.md`'s "WSL2 memory ceiling is a real, not theoretical, failure mode" section. Also hit, separately: Ollama's hardcoded 60s HTTP client timeout (`app/extraction/ollama_client.py`) was tuned around the small 1.5B model and genuinely too short for 7B/9B calls on CPU, observed live triggering false retries — fixed by making it configurable (`OLLAMA_TIMEOUT_SECONDS` env var, default unchanged at 60s for every other caller) rather than just raising the hardcoded constant for everyone.

**Error-surfacing design proven**: stopped the `ollama` container and called `/extract`, got back a real `502 {"detail": "Model-serving service unavailable"}`, not a silent empty response or a generic 500. Confirms the deliberate difference from the analytics instrumentation hook's best-effort design actually holds in practice.

**CI**: `fresh-volume-smoke-test` builds and scans the `extraction` image, starts it after `ollama` is healthy and models are pulled, and makes one real (not mocked) extraction call, asserting a real skill was matched with the correct requirement level.

**A real bug this CI check actually caught**: this exact smoke test failed in CI with `{"matches":[],"unmatched":[]}` against the unambiguous input "...must have strong experience with Python." Reproduced live, not assumed: 5 identical calls against the running service returned the correct match 3 times, an empty extraction once, and once took long enough to approach the client timeout, `qwen2.5:1.5b`'s sampled output for this prompt/schema combination is genuinely inconsistent, not a fluke of the test harness. Tried the obvious fix, pinning `temperature=0` (greedy decoding) to remove the sampling variance and it made things *worse*, not better: tested against 5 similarly-phrased skill-bearing sentences, greedy decoding returned the correct extraction for only 1 of them, an empty `[ ]` for the rest. The model's single most-likely completion for this task is often the degenerate empty answer; sampling actually escapes that local optimum some of the time. Fixed by retrying the LLM call (up to 3 attempts, `app/extraction/pipeline.py`'s `_MAX_EXTRACTION_ATTEMPTS`) only when the first attempt returns nothing at all extracted, verified live afterward: 8/8 repeated calls against the same input returned a match. This is a real resilience improvement for actual users, not just a CI patch, an empty extraction from obviously skill-bearing text was a real, previously undetected failure mode.

**CV upload, verified live against the real stack, not just unit tests**: uploaded a real PDF to `/candidates/1/cv`, confirmed the row landed in `candidate_documents` (correct filename/size), the object itself landed in SeaweedFS (`client.list_objects` showed `candidates/1/cv.pdf`, matching size), and `/candidates/1/cv/download` returned bytes that `diff`'d identical to the original file. Validation re-checked live too: a `.png` upload correctly returned `422` ("Only application/pdf is accepted"), a 3MB file correctly returned `422` ("File too large"), and an unknown candidate_id correctly returned `404` before ever touching object storage.

**Document-level confidence score and a human-in-the-loop review queue, since production has no ground truth to compute a real F1 against.** The golden-eval harness can measure precision/recall/F1 because real `CandidateSkill`/`JobSkill` ground truth exists for those examples; a real document submitted by a real user has none, so `/extract` needed its own heuristic quality signal instead. `pipeline._document_confidence(matches, unmatched)` combines the two things `extract_skills` already computes per phrase — average match `confidence` and the `unmatched`-phrase rate — into one 0-1 score per call: `avg_match_confidence * (1 - unmatched_rate)`, with an empty extraction from non-empty text scored 0.0 (a bad sign, not a neutral one) rather than left undefined. This isn't an untested guess: bucketing the ~5,700 examples across runs 29/32/34 by this exact formula and comparing against their real, ground-truth F1 showed a clean monotonic relationship (bucket avg confidence 0.04/0.33/0.51/0.71/0.92/1.00 → avg real F1 0.02/0.38/0.61/0.70/0.82/0.87), which is what set `_REVIEW_THRESHOLD = 0.6` — below that, real F1 on the golden data averages well under 0.65.

Every `POST /extract` call now persists a row to the new `extraction_calls` table (`app/extraction/models.py`, migration `282734230626`): model/embedding config, match/unmatched counts, `document_confidence`, `needs_review`, and `mlflow_trace_id` (captured via `mlflow.get_last_active_trace_id()` — not `get_current_active_span()`, which is already `None` by the time control returns to the route, since `extract_skills`'s own `@mlflow.trace` span has already closed). Two new endpoints turn this into an actual queue: `GET /review-queue` lists flagged-and-unreviewed calls, and `POST /review-queue/{id}/review` closes one out with a `reviewer` name, so the open backlog is a real, shrinkable number, not a running total.

**Two tools, two jobs, deliberately not duplicated**: the "JME Product Analytics" Grafana dashboard (`docker/grafana/provisioning/dashboards/jme-product-analytics.json`) got four new panels answering *how much/how often* — daily flagged-vs-ok call volume, the open (unreviewed) backlog as a stat tile with a red threshold, 7-day average confidence, and a table of the open queue itself. MLflow answers *why*, for one specific document: the queue table's `mlflow_trace_id` column carries a data-link out to that exact call's full per-phrase trace in the MLflow UI (`${MLFLOW_BASE_URL}/#/experiments/0/traces?selectedTraceId=...`, `MLFLOW_BASE_URL` a dashboard textbox variable defaulting to `http://localhost:5000`), so a reviewer or an on-call engineer can go from "this one needs a human" straight to "here's exactly what the LLM extracted and what the embedding step matched it to," without re-running anything. Neither tool tries to do the other's job: Grafana was never going to render raw match-confidence JSON well, and MLflow has no notion of "daily volume trending up."

Verified live, not just by reading the code: rebuilt and restarted the `extraction` service, called `/extract` with text that should extract cleanly (`document_confidence: 1.0, needs_review: false`), text with no real skills in it (`document_confidence: 0.0, needs_review: true`), and confirmed each call's row landed in `extraction_calls` with a real, non-null `mlflow_trace_id` — the first attempt used the wrong mlflow API and silently persisted `NULL` for every trace id, caught by actually checking the table rather than trusting the 200 response.

## Known Limitations

- No negation handling ("no Java experience required" would likely still extract "Java"), flagged as a known gap, not silently assumed away.
- Candidate can now upload and store a CV as a PDF (see "CV upload storage" above). What's still
  missing: the PDF's text is never parsed or run through `extract_skills` automatically, upload and extraction are two separate, deliberately un-chained steps in v1 (see Roadmap).
- Recall improved from 0.447 (original `llama3.2:1b`) to 0.60–0.68 (`qwen2.5:1.5b`) but is still not close to 1.0, some real skill mentions are still missed, most likely needing few-shot examples in the prompt to close the remaining gap further. Not yet attempted.
- Canonicalization threshold (0.55) was confirmed by a real sweep, not left as an unexamined first guess, but only five values were tried; a finer sweep could still find something better.
- The retry-on-empty-extraction fix (above) reduces, but does not eliminate, the chance of a real skill mention being missed, measured 8/8 successful on one specific input, not a guarantee across all inputs or a proof the underlying sampling inconsistency is actually resolved. A text that genuinely has no skills in it and one the model simply fails all 3 attempts on are indistinguishable to this fix; both return `{"matches": [], "unmatched": []}`.
- Synthetic CVs (the original 2000-candidate set) are structured/templated (name, summary, a skills list), not free-flowing resume prose, they exist to exercise the upload/storage/retrieval path end to end at real dataset scale, not to stress-test PDF text extraction against realistic formatting noise (headers/columns/tables). `docs/architecture/golden-evaluation-dataset.md` is exactly those "separate, messier fixtures": 500 real LLM-written resumes (and paired job postings) built specifically to eval extraction against natural prose, not a template echo.
- `document_confidence` is a heuristic proxy validated against the golden dataset's *aggregate* statistics, not a per-document guarantee — a specific document could still have high confidence and be wrong, or low confidence and be fine, the bucket-level correlation says the *rate* of bad extractions drops sharply above the threshold, not that any single flagged document is actually bad. The review queue has no UI yet either (`GET /review-queue` + `POST /review-queue/{id}/review` are the API; a reviewer currently needs to call them directly or through Grafana's table panel, not a dedicated screen).

## Roadmap

- **Parse the uploaded PDF's text and run it through `extract_skills` automatically**, a natural next step now that both halves exist independently, not built yet because PDF text extraction is a real, separate failure mode (scanned/image-only PDFs have no extractable text at all), deserving its own measured pass rather than being bolted on silently. `app/golden/run_extraction_eval.py` (`docs/architecture/golden-evaluation-dataset.md`) already does the PDF-to-text half via `pypdf` for *evaluation* purposes — this item is about wiring the same parse step into a real write path, not duplicating that work.
- **Wire extraction into a real write path**, only after the current pipeline is shown good enough: e.g. an endpoint that accepts raw text and actually populates `JobSkill` rows, at which point requirement-level output stops being only an eval metric and starts being operational data. Not scheduled yet.

## Resource Footprint and Scaling

**The one concurrent load test this project hadn't run**: `POST /extract` is the only live endpoint in the platform that calls Ollama synchronously (embeddings have no live endpoint at all, only the batch `embeddings-compute` job, `docs/architecture/ai-ml-and-mlops.md`), and it runs on a single uvicorn worker (`docker/Dockerfile.extraction` has no `--workers` flag) with a synchronous route, so concurrent requests share one process's threadpool before even reaching Ollama. Each call makes 1 LLM `generate()` call plus 1 embedding call per extracted skill phrase, sequentially (`app/extraction/pipeline.py`), real measured latency is both much higher and far more variable than the matching API's, dominated by how many phrases the LLM decides to extract per call, not primarily by concurrency.

Real `scripts/load_test_llm.py` results (concurrency 3 vs. 6, comparable mean skill counts per request): **throughput 0.28 -> 0.16 req/s, p95 latency ~18s -> ~58s**, the same queuing signature the matching API showed before its multi-worker fix, just at LLM-inference timescales. At concurrency 6 the tail latency (58.23s) sits right at the edge of `ollama_client.py`'s 60s per-call timeout. The two honest next steps, neither built here: give `extraction` multiple uvicorn workers (the same fix `api` already got), and address Ollama's own single-instance serialization (see `docs/architecture/ai-ml-and-mlops.md`), the first without the second would only move the queue from the process's threadpool to Ollama itself. Full numbers and methodology: `docs/operations/capacity-planning.md`.
