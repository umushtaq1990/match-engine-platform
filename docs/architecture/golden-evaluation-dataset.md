# Golden Evaluation Dataset

## Purpose & Scope

1000 candidates (originally 500 -- see "golden-dataset v2" below for why it grew and was regenerated), each given a realistic LLM-written CV and three LLM-written job postings deliberately constructed to be a near-perfect skill match, a real Keycloak login, and a persona-driven behavioral history. One dataset, built once, feeding three separate evaluation needs that previously had no good fixture:

- **Skill-extraction eval** against real natural-prose text, not text where the ground truth is visible by construction (see "Why the existing synthetic data wasn't enough" below).
- **Recommendation eval** against a *known* right answer per candidate (does the matcher actually rank a candidate's three true matches highly?), not just the population-wide "same occupation somewhere in the pool" ground truth.
- **Clustering / business-insights groundwork**: `app/analytics/segmentation.py` already names this project's planned "v3" (*"Real clustering (k-means/HDBSCAN) stays v3, only if \[rule-based segmentation\] is shown insufficient"*) — this dataset is what that v3 needs: deliberate, controlled diversity across both skill/occupation and behavioral-engagement axes. The actual k-means check now exists too (see the Live drill-down app section's "Unsupervised check" below) — built once the dataset was ready, not left as an assumption.

Explicitly **not** in scope here: a live per-request traffic simulator (hitting the real authenticated API) -- a natural follow-up, not built as part of this.

### Why the existing synthetic data wasn't enough

Two pre-existing generators share the same weakness: the "ground truth" is visible directly in the generated text, not hidden in natural prose the way a real extraction pipeline would actually have to work.

- **CVs** (`app/extraction/generate_synthetic_cvs.py`): a templated FPDF built mechanically from a candidate's own DB fields — trivial for the extraction pipeline to parse because the text *is* the structured data.
- **Job postings** (`app/ingestion/generate_synthetic_data.py:_build_job_description`): Faker boilerplate plus one fixed template sentence naming the required/preferred skills verbatim.
- **Recommendation ground truth** (`app/evaluation/ground_truth.py:build_ground_truth`): purely structural, `Candidate.primary_occupation_id == Job.occupation_id` — no signal about *how well* a candidate's actual skills match a job's actual requirements.
- **Candidates and Keycloak logins were fully decoupled**: all 2000 seeded candidates had zero login capability (issue #26's ownership model never needed one — the seeded dataset is deliberately "unowned").

## Architecture & Design

### Candidate selection (`app/golden/select.py`)

`select_golden_candidate_ids(session, n=500)` is the original, **pure, deterministic** function over already-seeded data — not a stored selection, and still used by anything that just needs "some deterministic subset." It only *reads* whatever `primary_occupation_id` a candidate already has; eligible ids are sorted by `(primary_occupation_id, id)` and strided evenly across that ordering so the selection spreads across occupations rather than favoring whichever one sorts first. As of golden-dataset v2 (below), the dataset's own candidates are chosen and populated by a different, newer function instead — `select_and_assign_golden_candidates(n=1000)`, which also *assigns* each one to a correctly domain-anchored occupation and regenerates its skills to match, not just reads what it already had. `select_existing_golden_candidate_ids` is the read-only lookup every downstream script (CVs, jobs, eval harnesses) uses to find "the golden candidates, right now."

### Golden CVs (`app/golden/generate_cvs.py`)

For each selected candidate, an LLM prompt (`qwen2.5:1.5b` via the existing `app/extraction/ollama_client.py`) writes a natural one-page resume from that candidate's real ground truth (name, years of experience, occupation, skills+proficiency) — explicitly instructed to avoid a rigid template or a bare "Skills:" bullet dump. Rendered to PDF with `fpdf2` and uploaded through the exact same real path a user upload goes through (`document_storage.validate_cv_upload`/`upload_cv`), marked with `original_filename == "golden_cv.pdf"` for idempotency.

Two real bugs surfaced and were fixed during the first live run, not assumed in advance:
- fpdf2's core "Helvetica" font is **latin-1 only** — LLM output routinely includes Unicode bullets/smart quotes/em-dashes, which crashed PDF rendering outright until sanitized (`_sanitize_for_core_font`).
- The LLM writes **Markdown** (`**bold**`, `# headings`) even though the render target is a plain-text PDF cell, not a Markdown renderer (`_strip_markdown`).

### Golden job postings (`app/golden/generate_jobs.py`)

Each candidate gets **three** independently LLM-written job postings, not one — a candidate whose matcher-returned top-3 contains 2-of-3 known positives is distinguishable from one with 0-of-3, which a single positive can't show. All three share the same *target* skill set (derived straight from the candidate's own `CandidateSkill` rows: `intermediate+` proficiency → `required`, `beginner` → `preferred`), but differ in company, title phrasing, and the LLM's independently-sampled prose — three genuinely different postings that should all still rank as strong matches, not three copies of one.

The explicit candidate→job mapping lives in a new `golden_pairs` table (`app/golden/models.py`), not encoded into a job's title/company as a string marker — a small, queryable table the recommendation-eval harness reads directly.

### Real Keycloak logins (`app/golden/provision_logins.py`)

Reuses `app/frontend/keycloak_admin.py`'s existing Admin-API client unchanged — the same one backing real self-registration, which already splits `full_name` into `firstName`/`lastName`. That turned out to matter: Keycloak 26's built-in `VERIFY_PROFILE` required action is enabled by default and resolves dynamically against the realm's User Profile schema regardless of any `defaultAction` flag, so a user created *without* those fields set (as this project's CI throwaway test user originally was, see `.github/workflows/ci.yml`'s history) fails every password-grant login with `invalid_grant: Account is not fully set up` even though every field the Admin API reads back looks complete. Reusing the production registration path sidesteps this entirely rather than re-deriving the fix.

Email/password are fully deterministic from `candidate_id` (`golden-candidate-{id}@example-synthetic.test` / a shared fixed dev password) — no credential manifest file is generated or stored, same spirit as the realm's existing checked-in dev-mode demo passwords.

### Persona-driven behavioral history (`app/golden/generate_persona_events.py`)

The generic event generator (`app/analytics/generate_synthetic_events.py`) assigns sessions uniformly at random across all 2000 candidates and always sets `received_at = now()`. That's a real problem for this dataset's purpose: `app/analytics/segmentation.py`'s recency feature is computed from `received_at` (the server-set, authoritative-for-ordering column), not the client-supplied `occurred_at` — so on the generic data, every candidate looks equally "just active" regardless of any assigned behavior, and the existing `GET /actors/candidate/{id}/segment` endpoint can never return anything but a volume-driven label.

Each of the 500 is assigned one of five persona archetypes, independently of occupation/domain (so skill-based and behavior-based structure aren't confounded), and the generator **deliberately backdates `received_at`**, grounded directly in `segmentation.py`'s real thresholds:

| Persona | Target rule-based segment | Pattern | Share |
|---|---|---|---|
| `power_applier` | `active_seeker` (via conversion ≥ 50%) | Frequent recent sessions, moderate shown-count, high click→apply conversion | 15% |
| `active_browser` | `active_seeker` (via volume ≥ 5 events/30d) | Frequent recent sessions, high shown/clicked volume, low conversion | 20% |
| `passive_seeker` | `passive_seeker` | One low-volume session within 30 days, rarely clicks, never applies | 30% |
| `dormant_recent` (churned) | `dormant` | A real burst of activity 45-90 days ago, then nothing since | 20% |
| `dormant_never_engaged` | `dormant` | Zero or one event total, 100+ days old | 15% |

A skewed, not uniform, distribution — deliberately, so a later business-insights narrative has something to say ("only 15% of candidates are highly engaged").

### Eval harnesses (`app/golden/run_extraction_eval.py`, `app/golden/run_recommendation_eval.py`)

- **Extraction**: reuses `app/extraction/run_extraction_eval.py`'s full persistence/metrics/MLflow pipeline unchanged via a small additive `examples` parameter — only the input dataset differs (golden CVs/jobs instead of generator-injected/hand-authored snippets). CVs are stored as PDFs, and this project has no existing CV-to-text pipeline (a documented, deliberately deferred gap) — this harness parses the real uploaded PDF bytes back to text via `pypdf` at eval time, so it genuinely exercises "real CV bytes in, skills out," not a cached-text shortcut.
- **Recommendation**: calls `app/matching/rank.py:rank_jobs_for_candidate` directly (not routed through `app/evaluation/run_evaluation.py`, simpler and more decoupled than threading a new parameter through the production harness for a need only this golden set has) and checks how many of each candidate's 3 `golden_pairs` jobs land in their real top-K — precision@3/recall@3 against known positives.
- **Second serving backend**: `--backend {ollama,vllm}` (`app/golden/vllm_client.py` alongside the existing `app/extraction/ollama_client.py`), added specifically so this same harness could compare model families/sizes across both a CPU-served Ollama path and a GPU-served vLLM path without duplicating the eval logic per backend — see `docs/architecture/application-services/skill-extraction.md`'s model-comparison results for what it found.
- **Targeted "hard case" re-evaluation** (`--hard-cases-f1-below <threshold> --compare-run-ids <ids>`): rather than re-running the full dataset (a 14-18+ hour CPU job per bigger model) to test whether a larger model actually helps, this queries `extraction_example_results` for the subset of examples where every one of the given prior runs already scored below the threshold, and evaluates only that subset against the new model. A general, reusable capability (`_hard_case_example_ids`/`_examples_by_ids` in `app/golden/run_extraction_eval.py`), not a one-off script, because "does a bigger/different model help on the cases that are actually hard" is a question worth asking again whenever a new model candidate shows up.

### Decomposition-tree report (`app/golden/build_evaluation_tree.py`)

A business-facing "where exactly is the score good or bad" view, requested directly: overall F1 drilling down into one of 4 profession domains (`SKILL_DOMAINS` in `generate_synthetic_data.py` — `software_engineering`, `business_ops`, `trades_logistics`, `people_services`) then into individual occupations, built separately for candidates (500 CVs) and job posts (1500 postings) so each branch's leaf counts sum to exactly those numbers. Grafana has no decomposition-tree/sunburst visual, so this renders a single self-contained Plotly Icicle chart to `data/golden/reports/evaluation_drilldown_run<id>.html` (plotly.js inlined — opens in any browser, no server, shareable as one file) — the open-source equivalent of Power BI's/Tableau's decomposition tree. Run via `docker compose run --rm golden-eval-tree [--run-id N]` (defaults to the best-scoring full-2000-sample run).

Two real data-quality issues were found and fixed while building this, not assumed away: (1) occupations are seeded by cycling a short list of real titles with a numeric suffix once the list runs out (`"Welder 4"`) — the first version of this report fragmented into ~170 near-duplicate 1-5-count leaves until titles were canonicalized back to the base profession; (2) each occupation's *domain* in the seed data (`occupation_skills`) is anchored **uniformly at random** per occupation row (`_assign_domain_anchored_skills` → `rng.choice(domain_names)`), with no semantic link to the title — it exists purely to give the skill co-occurrence graph (`docs/knowledge-graph.md`) real community structure, not to encode a real professional taxonomy. Confirmed live: before this was caught, "Welder" (and every other title with multiple padding rows) showed up scattered across multiple domains depending on which row got sampled — technically faithful to the seed data, but nonsensical to a business reader. Fixed with an explicit, human-judged `_CURATED_OCCUPATION_DOMAINS` map for the 26 real occupation titles (data-driven skill-category majority vote stays as the fallback for anything not in that list, e.g. user-added occupations).

One finding this surfaced immediately, worth carrying into any read of the golden-eval numbers elsewhere in this doc or in `skill-extraction.md`: candidate CVs extract substantially better than job postings in *every* domain (e.g. run 30: trades_logistics CVs 0.94 avg F1 vs. trades_logistics job posts 0.77) — not a fluke of one domain, a consistent gap across all 4.

### golden-dataset v2: the fix goes deeper than the report (occupations, scale, GPU, noise)

The hand-curated domain map above papered over a *labeling* bug in the report, but digging further (prompted directly: "did you check yourself if it makes sense?") found the real bug was upstream and much bigger: `occupation_skills`' domain anchor is picked **uniformly at random per occupation row**, with zero link to its title — true for all 150 base occupations, curated titles included, not just padding duplicates (confirmed via direct SQL: curated-vs-padding status predicts nothing about F1, ~0.92 vs ~0.93 for CVs). The concrete, confirmed case: job #1456, a genuine, LLM-written welding/metal-fabrication posting titled "Welder 2," whose *required* ground-truth skill was **"Django"** — never mentioned anywhere in its text. 81% of the original 500/1500 golden set (407 candidates, 1221 jobs) sat on occupations with this kind of title/skill mismatch.

Now that vLLM/GPU generation exists (~15 req/s vs. Ollama's ~0.3-0.6 req/s), regenerating the golden set properly became cheap enough to do rather than patch around:

- **A real, expanded occupation taxonomy, fixed at the root.** `app/ingestion/generate_synthetic_data.py`'s `SKILL_DOMAINS` grew from 4 domains to 8 (`technology`, `healthcare`, `skilled_trades`, `business_finance`, `sales_marketing`, `education`, `creative_media`, `logistics_operations`), and a new `CURATED_OCCUPATION_DOMAINS` map gives ~43 new occupation titles (`app/golden/seed_curated_occupations.py`) a domain anchored *deterministically* to the correct one, not `rng.choice`. `Occupation.domain` and `Skill.skill_type` (technical/soft -- a more meaningful axis than requirement_level, which `set_precision`/`set_recall`/`set_f1` in `app/extraction/metrics.py` already score over the combined skill set, never split by required/preferred) are now real persisted columns. Purely additive -- the original 150 base occupations are untouched; a handful of thin categories (healthcare, education, sales, logistics) got new skills (`GOLDEN_V2_NEW_SKILLS`) to anchor a believable profile from, and the pre-existing "Sales" skill was retagged from "business" to a new "sales" category (a label change only).
- **Candidates are now reassigned, not just selected.** `app/golden/select.py`'s new `select_and_assign_golden_candidates(n=1000)` round-robins 1000 candidates evenly across the 43 new curated occupations and regenerates their `CandidateSkill`/`CandidateSkillAssessment` rows to actually match (same anchor/noise mechanic as the base seed, just correctly anchored) -- the real fix, not a relabeling. `select_golden_candidate_ids` (the original, which only *reads* whatever occupation a candidate already had) stays for anything that still needs it; `select_existing_golden_candidate_ids` is the new canonical "who are the golden candidates right now" lookup every downstream script uses (`Occupation.domain IS NOT NULL` is unambiguous for this).
- **Scaled 500→1000 candidates, 1500→3000 jobs**, generated via `--backend vllm` (`app/golden/generate_cvs.py`/`generate_jobs.py`, `app/golden/llm_retry.py`'s `make_generate_with_retry` generalized to accept either backend, moved out of a private copy that used to live in `run_extraction_eval.py`).
- **Full regenerate, not a top-up**: `app/golden/wipe_golden_dataset.py` deletes the old golden CVs/jobs/pairs/eval-runs (never the base seed pool) before rebuilding, since topping up 500 old (bug-affected) with 500 new would leave a mixed-quality set.
- **Deliberate noise injection** (`app/golden/inject_noise.py`, new `golden_injected_noise` table): ~10% of golden candidates and ~10% of golden jobs, independently, get 1-2 unrelated skills added to their ground truth *after* their text is already written, picked from a domain unrelated to their own -- guaranteed not mentioned in the text by construction. Every injection is recorded (which example, which skill) so a **later** pass (explicitly not built here) can check whether extraction, or the confidence-scoring review queue (`app/extraction/pipeline.py`'s `_document_confidence`, see `skill-extraction.md`), actually flags these as data-quality issues.
- **The decomposition-tree report now renders two trees side by side**, not one: the original (entity type → domain → occupation, by F1) plus a new one over skill *matches* rather than examples (entity type → domain → occupation → skill type, by average match confidence) -- skill type is a property of a matched skill, not a whole example, so it can't be a 4th level of the same per-example tree without double-counting a CV that has both technical and soft skills.

**A real bug the live run caught**: `inject_noise.py`'s first version picked an "unrelated domain" skill without checking whether the candidate/job already happened to hold it as part of their own normal cross-domain noise (the ~20-30% `_assign_fixed_domain_skills` mixes into every profile) -- hit a real `candidate_skills`/`job_skills` unique-constraint violation on the live run, fixed by excluding already-held skill ids from the pick (regression-tested, `tests/golden/test_inject_noise.py`).

**Concurrency matters, confirmed live**: the first full eval run against the new set used the eval harness's default `--workers 1` (sequential) -- 28 minutes in, only 22% done (≈31 examples/min). Killed and restarted with `--workers 8`: ≈152 examples/min, a ~5x improvement (not the full 8x, since the embedding step shares Ollama's own `OLLAMA_NUM_PARALLEL=5` cap). The earlier "~15 req/s" vLLM throughput figure elsewhere in this doc was always about *concurrent* request handling -- sequential calls (the default for `generate_cvs.py`/`generate_jobs.py`, which have no `--workers` flag at all) only benefit from vLLM's lower per-call latency, not its real architectural advantage.

**Final result** (`run_id=38`, `Qwen2.5-3B-Instruct-AWQ` via vLLM, `--workers 8`, full 4000 examples = 1000 CVs + 3000 jobs): **precision 0.8911 / recall 0.7962 / F1 0.8273** -- higher than the old (bug-affected) dataset's best F1 of 0.7916, despite 10% of examples now deliberately carrying an unfindable injected skill. Domain/occupation breakdown confirmed clean: every one of the 43 curated occupations maps to exactly one domain across all 4000 examples (verified directly, zero exceptions) -- the scattering bug this whole effort started from is gone. One finding worth flagging, and a reversal of the old dataset's pattern: job postings now score *higher* than candidate CVs in every domain (e.g. technology: jobs 0.914 vs. candidates 0.814; skilled_trades: jobs 0.885 vs. candidates 0.798) -- the opposite of what the old, bug-affected dataset showed, and a genuinely different signal worth a fresh look rather than assuming the old explanation still holds. (`run_id=37` was this same config's first pass, superseded by 38 once `mlflow_trace_id` capture was added to the eval harness -- the two differ only by LLM sampling noise, 0.8237 vs. 0.8273.)

### Full traceability (`mlflow_trace_id` on `extraction_example_results`, noise-detection results)

A real gap closed, not assumed closed: `extraction_example_results` had no way to reach a specific example's MLflow trace at all -- unlike the production `extraction_calls` table, which already had `mlflow_trace_id` from the earlier confidence-scoring work. Added the same column here, captured the same way (`mlflow.get_last_active_trace_id()` right after `extract_skills()` returns, inside `app/extraction/run_extraction_eval.py:_extract_one`), confirmed to work correctly even under `--workers 8`'s concurrent threads (MLflow's tracing context is thread-local) -- all 4000 examples in run 38 have a real, non-null trace id.

**The noise-detection check this was all building toward, now run, with a real (negative) result**: does the confidence-scoring review-queue mechanism (`app/extraction/pipeline.py`'s `_document_confidence`, `_REVIEW_THRESHOLD=0.6`) actually catch the deliberately injected, unfindable skills from `app/golden/inject_noise.py`? Computed retroactively from each example's already-persisted `match_detail`/`unmatched_detail` (`app/golden/analyze_noise_detection.py`, no new extraction calls) against run 38:

| | count | avg document_confidence | flagged (confidence < 0.6) |
|---|---|---|---|
| Noise-injected | 400 | 0.8438 | 37 (9.2%) |
| Clean | 3600 | 0.8442 | 327 (9.1%) |

**It doesn't work, and the reason is structural, not a tuning problem.** The detection rate (9.2%) is statistically indistinguishable from the false-positive rate on clean examples (9.1%) -- the mechanism has essentially zero discriminative power for this specific failure mode. Why: `_document_confidence` is computed entirely from what the LLM *did* extract from the text (`match_detail`/`unmatched_detail`) -- it has no access to ground truth, in production or here. A deliberately injected skill is, by construction, never mentioned in the text at all, so it never appears in either `match_detail` or `unmatched_detail` -- it's invisible to this signal, not weakly detected by it. A document missing one required skill and an otherwise-identical document that never had that requirement look *identical* to `_document_confidence`, because the heuristic can only ever judge "how confident is the model in what it found," never "is anything missing" -- that second question needs real ground truth (or at least a reference requirement list), which production doesn't have and this check deliberately didn't give the heuristic either, to test it honestly. One genuine anomaly, spot-checked rather than left as a footnote: 1/400 injected skills wrongly ended up in `match_detail` anyway, for `golden_cv:240`. The injected skill was "Social Media," and this candidate's real occupation title happens to be "Social Media Manager" -- the LLM-written CV naturally uses that real, legitimate title in its prose ("Highly experienced Social Media Manager..."), and extraction then matched that phrase to the canonical skill named "Social Media." A text-string coincidence between an occupation title and a skill name, confirmed by reading the actual generated CV, not the model genuinely inferring a missing competency.

**Corrected precision/recall/F1, now that we know exactly which skill was injected into which example**: stripping the one known-fake skill from `expected_skill_ids` before rescoring gives an honest read of the model's real extraction quality, undeflated by ground truth we know is deliberately wrong (the raw metrics in `extraction_runs` are never touched -- this is a separate report on top of already-persisted data, not a rewrite of how the run was scored):

| | Precision | Recall | F1 |
|---|---|---|---|
| Original (`extraction_runs.f1_avg` for run 38) | 0.8911 | 0.7962 | 0.8273 |
| Corrected (injected skill excluded from expected set) | 0.8911 | **0.8068** | **0.8337** |

A real, if modest, effect (+0.64 F1 points) -- precision is unaffected (it's about what the model predicted, not what ground truth claims), recall and F1 both recover once the known-fake requirements are excluded. `app/golden/analyze_noise_detection.py` now prints both numbers on every run, so this is a repeatable report, not a one-off calculation.

This is a real, useful finding for anyone relying on this review-queue mechanism in production: it's a precision-side safety net (catches "the model found something it's unsure about"), not a recall-side one (does nothing for "the model silently missed a requirement"). Closing that gap would need a different mechanism -- e.g. cross-referencing against an expected-requirements profile per occupation, which this project doesn't have built.

**A different idea, tested the same way, does better: does a skill look out of place next to the rest of the list, rather than how confident the extraction was.** Two variants tried against the same 400 noisy / 3600 clean examples, scored on `expected_skill_ids` directly (not on what got extracted):

| Approach | Best usable point | Recall | Precision | False-positive rate |
|---|---|---|---|---|
| Confidence heuristic (above) | only threshold that exists | 9.2% | -- | 9.1% (no separation at all) |
| Domain-category majority vote (count of skills whose `SKILL_DOMAINS` category differs from the list's majority) | outlier count ≥ 3 | 68.0% | 48.9% | 7.9% |
| Embedding centroid similarity (leave-one-out cosine similarity of each skill's `nomic-embed-text` embedding against the mean of the rest) | best threshold found | 84.5% | 2.5% | 53.7% |

The coarse, hand-curated category labels (`SKILL_DOMAINS`) beat the embedding-based version by a wide margin, which is a real, somewhat counter-intuitive finding worth remembering: `nomic-embed-text` is a general-purpose sentence embedding model, not fine-tuned to cluster skills by domain, and averaging several skill embeddings into a centroid doesn't land on a meaningful "semantic center" for this purpose -- the two populations' average similarity barely differs (0.553 noisy vs. 0.595 clean). The domain-majority-vote version is noisy specifically because this dataset's own clean skill profiles are deliberately built with ~20-30% natural cross-domain noise (`_assign_fixed_domain_skills`), so "has an outlier" alone can't separate clean from corrupted -- only "has *several* outliers" gets real separation. Neither approach is built into the actual review-queue mechanism; both were validated here as an answer to "how would you actually catch this," not shipped as a feature.

### Live drill-down app (`app/golden/drilldown/`)

A persistent, interactive counterpart to the static report above, requested directly after someone asked to actually click into a leaf (e.g. "Job Posts → healthcare → 72 Medical Assistant postings") and see every underlying record -- scores, expected/matched/unmatched skills, text preview -- not just the aggregate box. A static HTML file can't do that (no backend to query on click), so this is a small, long-running Streamlit service, three pages:

- **Candidates & Job Posts** (`pages/1_Candidates_and_Jobs.py`): the same entity-type → domain → occupation tree as the static report, by F1. Each record's row carries a clickable **MLflow trace** link and, where applicable, which skill `inject_noise.py` deliberately planted in its ground truth (a "noise-injected only" checkbox filters straight to those).
- **Skills** (`pages/2_Skills.py`): entity-type → domain → occupation → skill type (technical/soft), by match confidence -- the same "two trees, two units" split as the static report (skill type is a property of one matched skill, not a whole example). Same MLflow trace link per matched skill.
- **Behavioral Analytics** (`pages/3_Behavioral_Analytics.py`): the persona each golden candidate was deliberately assigned vs. the *actual* rule-based segment that behavior produces (`app/analytics/segmentation.py`, unchanged, real production logic, not reimplemented) -- cross-tabbed against the same domain/occupation taxonomy the other two pages use. **Unsupervised check**: k-means (k=5, matching the 5 personas directly) over the same behavioral KPIs (`app/golden/drilldown/data.py:compute_behavioral_clusters`) -- the actual "v3" clustering `app/analytics/segmentation.py`'s own docstring named as a future step, built once this dataset existed to support it, not left as an assumption either way.

**The clustering result is real, and genuinely mixed -- not a clean "it works" or "it doesn't."** Run against the live 1000: `active_browser` recovers almost perfectly as its own cluster (200/201 -- one stray `dormant_recent`), and `power_applier` splits cleanly into two sub-clusters (61 + 86, likely differing by conversion-rate magnitude) that are both still unambiguously power-applier. But `dormant_recent` (199/200), `passive_seeker` (300/300), and about half of `dormant_never_engaged` (67/150 -- specifically the ones who got the rare single login event, not the ones with zero events at all) all collapse into one shared cluster. These three personas are numerically similar on the five KPIs used (low/no recent activity, low event counts) -- k-means at k=5 can't tell "a real burst 45-90 days ago, then silence" apart from "always been quiet" apart from "logged in once, years ago" using only `days_since_last_event`/`event_count_window`/`shown_count`/`applied_count`/`conversion_rate`. A feature that captures *when* past activity happened (not just whether there's been any recently) would likely be needed to separate them -- not built here.

All three pages share one run picker (`app/golden/drilldown/data.py:select_run_in_sidebar`) and reuse `build_evaluation_tree.py`'s `_icicle_trace`/`_aggregate` directly (`app/golden/drilldown/chart.py`) rather than reimplementing the hierarchy logic. Drilling down is via a set of cascading dropdowns below the chart, narrowing down to a full detail table of every matching record.

**Click-to-drill on the chart itself was tried and confirmed not to work, not just assumed to be risky.** `st.plotly_chart(fig, on_select="rerun")` *does* fire a Streamlit rerun when the chart is clicked, but `event["selection"]["points"]` comes back an empty list every time for an Icicle trace — tested live twice (plain click, and again with `fig.update_layout(clickmode="event+select")`, the one documented lever for this), same empty result both times. Root cause: Streamlit's `on_select` is built around Plotly's generic "selectedpoints" mechanism (what scatter/bar/etc. use); Icicle/Sunburst/Treemap charts fire their own separate click event family in Plotly.js that Streamlit doesn't bridge to Python. A real, current gap in Streamlit's chart-selection support, not a config mistake — the cascading dropdowns are the one real navigation mechanism here, not a fallback for a flakier primary one.

Verified live without a browser (none was available in this environment) via Streamlit's own `AppTest` framework, which actually executes the script rather than just checking an HTTP 200: all four pages (Home + the three above) render exception-free, and simulating the exact drill-down above (Job Posts → healthcare → Medical Assistant) via `AppTest.selectbox(...).select(...).run()` produced exactly 72 matching rows -- confirmed directly against the DB first, then reproduced through the app's own filtering code. `AppTest` can only drive widgets like selectboxes, though, not a chart's click event — the click-to-drill investigation above needed the real running app and `docker logs`, confirmed by a human actually clicking it, not something `AppTest` could have caught either way.

Run with `docker compose up -d golden-drilldown`, open `http://localhost:8502` -- a long-running server (`up -d`), not a one-off script, even though it shares the "tools" profile with the rest of this package. Deliberately doesn't fetch candidate CV text (would need SeaweedFS credentials in yet another service for a lower-value payoff) -- job posting text shows directly since `description_raw` is already plain text in the DB.

**`golden-logins`/`golden-events` needed the same v2 candidate-lookup fix as the generation scripts, and running them surfaced real stale data.** Both still called the original `select_golden_candidate_ids` (reads whatever occupation a candidate already has, the exact mechanism the v2 rework replaced) instead of `select_existing_golden_candidate_ids` -- fixed the same way `generate_cvs.py`/`generate_jobs.py` were. Running `golden-events` afterward found `analytics.behavioral_events` had `golden_persona`-sourced rows for **1152** distinct candidates, not 1000 -- leftover from the original v1 golden set (candidates no longer golden kept their old events; some overlapping ids would have been double-counted too). Wiped every `source = 'golden_persona'` row and regenerated cleanly for exactly the current 1000 before trusting any of it for the Behavioral Analytics page. Re-verified the persona→segment mapping on the clean data the same way the original build did: 99/100 on a sample matched: the one mismatch (candidate 1) has real, unrelated `source = 'api'` events from earlier manual testing in this same environment contaminating its recency signal -- a known, pre-existing confound affecting 3/1000 candidates total, not a new bug.

### Backup & restore (`app/golden/export_backup.py`, `app/golden/restore_backup.py`)

The CVs and job postings are the only expensive-to-regenerate part of this dataset (~2,000 Ollama calls) — logins and behavioral events are fast/deterministic (Keycloak admin calls, seeded RNG) and cheaper to just re-run than to back up. `golden-export` downloads all 500 CV PDFs from object storage and dumps every golden job's full `Job`/`JobSkill`/`GoldenPair` data to `data/golden/backup/` (git-ignored, a local recovery copy, not checked into version control). `golden-restore` reads it back, idempotently (same "already present" markers as the generators), re-uploading CVs and re-inserting jobs without calling Ollama at all — recovers a wiped Docker volume in seconds instead of hours. Logins/events still need `golden-logins`/`golden-events` run afterward (fast, not part of the backup).

## Verification & Results

- All 8 scripts smoke-tested with `--limit N` against the real local stack before any full run: CV generation (inspected actual rendered PDF content by eye — realistic, natural prose, not a template echo), job generation (3 independently-written postings per candidate, same skill ground truth, verified via direct DB query), login provisioning (confirmed an actual password-grant token exchange succeeds against the newly created account), persona events (verified against the *real* `segment_actor()` function, not assumed: 0/100 mismatches between assigned persona and returned segment on a 100-candidate sample, after two real bugs in the passive-seeker volume tuning were found and fixed this way), extraction eval (real, non-trivial precision/recall numbers — not all-zero or all-perfect, which would indicate a bug rather than a real signal), recommendation eval (recall@10 = 1.0 and precision@10 = 0.3 for the one fully-generated test candidate — all 3 golden jobs found).
- A real transient Ollama timeout crashed the first attempt at the full 500-candidate CV batch on the very first candidate (confirmed live, not theoretical) — fixed with a small retry wrapper (`app/golden/llm_retry.py`) and per-candidate exception handling in both `generate_cvs.py` and `generate_jobs.py`, so one candidate's persistent failure no longer aborts a multi-hour batch; a future re-run simply tops up whatever's still missing.
- Unit tests: `tests/golden/test_select.py` (determinism, occupation spread, exclusion rules — DB-backed), `tests/golden/test_generate_persona_events.py` (persona-assignment determinism and distribution), `tests/golden/test_text_cleanup.py` (the two real rendering bugs above, regression-guarded).

## Known Limitations

- LLM generation cost was real under Ollama (~2000 total CPU inferences for the original 500×(1 CV + 3 jobs) batch, each 8-30s warm — hours of wall-clock time), mitigated by resumability rather than by making it fast. v2's 1000×(1 CV + 3 jobs) = 4000 calls via `--backend vllm` is the actual fix for this, not just a workaround (minutes, not hours, on this GPU).
- The persona→segment mapping is probabilistic, not guaranteed, by the nature of a rule-based threshold applied to randomly-sampled event counts/timing — verified at 99/100 on a sample against the clean, re-derived golden 1000 (the one mismatch is a known, pre-existing confound from unrelated test data, not a flaw in the mapping itself).
- No live per-request traffic simulator yet — the persona events are bulk-inserted with backdated timestamps (fast, controls the statistical distribution precisely), not generated by hitting the real authenticated API end-to-end. A smaller, complementary script using the real logins from this dataset is a natural follow-up for demonstrating the live pipeline, not how the bulk historical volume here was built.
- The domain/skill_type taxonomy (8 domains, technical/soft) is a documented judgment call, same as the original 4-domain one it replaced -- not claimed to be scientifically rigorous.
- The k-means check (drill-down app, Behavioral Analytics page) runs live, in-process, every time the page loads -- fine at 1000 rows/5 KPIs, but it's recomputed on every page view, not cached or persisted anywhere; a much larger golden set would want that memoized.
- The confidence-scoring review queue's blind spot to missing-required-skill noise (documented above) is a finding about that mechanism, not something this dataset fixes -- closing it would need a different mechanism entirely (e.g. an expected-requirements profile per occupation), not built here.

## Roadmap

- A live traffic simulator using the real golden logins, to demonstrate the full authenticated request path (not just bulk-inserted history) producing behavioral events in near-real-time on the "JME Product Analytics" Grafana dashboard.
- Extending `golden_pairs` with graded "distractor" jobs (partial, not near-perfect, skill overlap) if finer-grained ranking evaluation is ever needed beyond precision@3/recall@3.
- A detection mechanism for the missing-required-skill blind spot the noise-detection check found -- the review queue's current heuristic structurally can't see it (no ground truth to compare against); a per-occupation expected-requirements profile is the most obvious next idea, not yet designed.
